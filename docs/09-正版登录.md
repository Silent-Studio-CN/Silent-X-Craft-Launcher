# 09 · 正版登录(微软 / Xbox Live)

本文覆盖 **Silent-X-Craft-Launcher C 版**的正版登录核心库(纯 C11,零第三方依赖;TLS 交给 `sxcl_transport`)。

- 代码:`include/sxcl/auth.h`(对外契约)、`include/sxcl/auth_store.h`(加密落盘)、`src/core/auth/**`
- 命令行:`sxcl-dl auth <login|status|refresh|logout|bedrock>`
- 测试:`src/core/auth/tests/**`(夹具在 `tests/fixtures/auth/`,**不联网也能全绿**)

一句话设计:**把登录拆成一条明明白白的链,每一跳都自己拿到凭据,失败就停在那一跳并说清原因。**
绝不做从上一跳推断下一跳这种事 —— 那是启动器鉴权 bug 的头号来源。

---

## 1. 链路图(Java 版)

```
         +------------------- 步骤 1:拿到微软 access_token -------------------+
         |                                                                     |
[主路]   | GET  https://login.microsoftonline.com/<租户>/oauth2/v2.0/authorize |
授权码流 |      ?response_type=code&client_id=...                              |
         |      &redirect_uri=http://localhost:<随机端口>/callback              |
         |      &scope=XboxLive.signin offline_access                          |
         |      &code_challenge=<S256(verifier)>&code_challenge_method=S256    |
         |      &state=...&prompt=select_account                               |
         |       |- 本进程起一个**只监听 127.0.0.1** 的短命 HTTP 服务(端口随机) |
         |       |- 用系统默认浏览器打开这个 URL                                |
         |       |- 浏览器授权后跳到 /callback?code=...&state=...               |
         |       |- 校验 state(**不一致就丢弃,继续等**)后收下 code               |
         | POST https://login.microsoftonline.com/<租户>/oauth2/v2.0/token     |
         |      grant_type=authorization_code&code=...&redirect_uri=...&code_verifier
         |                                                                     |
[兜底]   | POST .../oauth2/v2.0/devicecode                                     |
设备码流 |      -> user_code + verification_uri + interval + expires_in         |
         |      (把 user_code 打给用户,让他在浏览器里输入)                      |
         | POST .../oauth2/v2.0/token   每 interval 秒轮询一次                  |
         |      grant_type=urn:ietf:params:oauth:grant-type:device_code         |
         +-----------------------------+---------------------------------------+
                                       | 微软 access_token + refresh_token
                                       v
  [3] POST https://user.auth.xboxlive.com/user/authenticate
        { Properties: { AuthMethod:RPS, SiteName:user.auth.xboxlive.com,
                        RpsTicket: "d=<微软 access_token>" },
          RelyingParty: "http://auth.xboxlive.com", TokenType: JWT }
        -> XBL Token + DisplayClaims.xui[0].uhs
                                       |
                                       v
  [4] POST https://xsts.auth.xboxlive.com/xsts/authorize
        { Properties: { SandboxId: RETAIL, UserTokens: [ <XBL Token> ] },
          RelyingParty: "rp://api.minecraftservices.com/", TokenType: JWT }
        -> XSTS Token + uhs      (失败时 401 + XErr 数字,见 4 节)
                                       |
                                       v
  [5] POST https://api.minecraftservices.com/authentication/login_with_xbox
        { identityToken: "XBL3.0 x=<uhs>;<XSTS Token>" }
        -> Minecraft access_token (expires_in 86400)
                                       |
                   +-------------------+-------------------+
                   v                                       v
  [6a] GET .../entitlements/mcstore          [6b] GET .../minecraft/profile
       Authorization: Bearer <MC token>         Authorization: Bearer <MC token>
       -> items[]  (买了才有条目;404 = 没买)     -> id / name
                                                 **name 为空 / 404 = 没有 Java 版**
                                       |
                                       v
  [7] 免密续期:POST .../oauth2/v2.0/token
        grant_type=refresh_token&refresh_token=...&scope=XboxLive.signin offline_access
        -> 新 access_token (+ 可能轮换的新 refresh_token) -> 回到 [3] 重跑
```

**步骤 6 的两条不是同一件事**,所以两条都查、分开报:

| 接口 | 回答的问题 | 我们的结论 |
| --- | --- | --- |
| `entitlements/mcstore` | 这个账号在商店里有没有 Java 版记录 | `mc.entitlement_count` / `mc.entitlements_checked` |
| `minecraft/profile` | 这个账号有没有可用的 Java 版档案 | `mc.name` / `mc.uuid`;name 为空或 404 就返回 `SXCL_AUTH_ERR_NO_PROFILE` |

**绝不允许**名字取不到就用默认名继续启动 —— 那会让用户带着一个坏身份进游戏,报错更难查。

## 2. 基岩版:同一条登录派生的**第二条链**

基岩版不是另一次登录,而是**同一份微软/Xbox 凭据派生出的另一条授权链**:

```
  同一份微软 access_token
    -> [3] XBL 用户认证(与 Java 相同)
         -> [4b] XSTS,**中继方换成 https://multiplayer.minecraft.net/**
              -> [5b] POST https://multiplayer.minecraft.net/authentication
                       { identityPublicKey: "<base64 P-384 未压缩公钥>",
                         certificate: null,
                         token: "XBL3.0 x=<uhs>;<XSTS Token>" }
                    -> { chain: [ <JWT>, ... ] }   <-- 进官方基岩客户端要用的证书链
```

**权益为什么必须分开谈**:Java 版与基岩版是**两次独立购买**。

- 基岩侧没有 `mcstore` 那样的公开权益接口:**能不能拿到 `chain` 本身就是判据**
  (没买时服务端拒绝,实测为 HTTP 403)。
- 因此 `sxcl_auth_bedrock_tokens` 里单独存 `entitlement_checked` / `entitled`,
  与 `sxcl_auth_minecraft_tokens` **互不影响**:Java 买了不代表基岩买了,反之亦然。

身份密钥用内置的 P-384 生成器(`src/core/auth/ec384.c`):私钥 48 字节取自系统 CSPRNG,公钥 = d*G,
导出未压缩点(`0x04 || X || Y`,97 字节)的 base64。参数与标量乘法用 **RFC 5903 第 3.2 / 8.2 节的官方向量逐位对拍**
(见 `auth_bedrock_test`),所以标量乘法写错了这种事不可能悄悄溜过去。

### 租户段(`<租户>`)必须与应用的受支持账户类型一致

| 应用注册里的受支持的帐户类型 | 该用哪个租户段 |
| --- | --- |
| 仅个人 Microsoft 帐户 | `consumers`(**本仓库默认**) |
| 任何组织目录中的帐户 + 个人帐户 | `common` |
| 仅我的组织(单租户) | 该租户的 id 或域名(用 consumers / common 会被拒) |

### 4.3 Minecraft 服务端的 HTTP 码

| HTTP | 我们怎么解释 |
| --- | --- |
| 401 | 登录凭据被拒绝(XSTS / identityToken 不被接受) |
| **403** | 两种可能:(a) **该应用没在 Mojang 登记过**,正文是 Invalid app registration, see https://aka.ms/AppRegInfo ;(b) 基岩链上表示**这个账号没有基岩版权益** |
| 404 | mcstore:确实没有权益;profile:没有 Java 版档案(ERR_NO_PROFILE) |
| 429 | 被限流,稍后再试 |

### 4.4 我们自己的返回码(sxcl/auth.h)

SXCL_AUTH_ERR_NET / HTTP / JSON / DENIED / EXPIRED / TIMEOUT / CANCELLED / XBOX / NO_PROFILE / NO_ENTITLE / STORE / UNSUPPORTED / NOMEM / RATE_LIMIT。
CLI 把返回码一起打出来(例如 返回码 -6),便于对照本表定位。

## 5. client_id 与租户段怎么配

**优先级(只此一套,别在别处再写一遍)**:

```
命令行/API 显式参数  >  环境变量  >  sxcl_settings  >  内置默认
client_id: --client-id   SXCL_AUTH_CLIENT_ID   auth.client_id   aa4e81c8-f550-4720-bc51-c9b126f456d1
租户段:    --tenant      SXCL_AUTH_TENANT      auth.tenant      consumers
```

- 解析函数:`sxcl_auth_resolve_client_id()` / `sxcl_auth_resolve_tenant()`
  校验:`sxcl_auth_client_id_valid()`(只允许 [0-9A-Za-z._~-],长度 8..127)、
  `sxcl_auth_tenant_valid()`(只允许 [0-9A-Za-z.-],**挡住 ../ 之类改写端点路径**)。
- 形状不对时**在发请求之前**就报错(测试断言:一个请求都不会发出去)。
- **仓库里只有 client_id**(它本来就是公开信息),**任何 secret 都不许进代码/仓库**。公共客户端本来也不该有 secret。

内置默认值 = 本项目在 Azure 注册的应用 **Silent X Craft Launcher**:
`aa4e81c8-f550-4720-bc51-c9b126f456d1`,注册为**公共客户端**(移动和桌面应用程序,重定向 http://localhost),
受支持的帐户类型 = 仅个人 Microsoft 帐户,所以租户段用 `consumers`。
选它当默认的理由:合规(是我们自己的应用)、可控(配置、限额、改名都由我们决定)。

**社区公共 id `00000000402b5328` 依然可以通过配置使用**,但**实测它在 microsoftonline.com 上根本不可用**(见 9.3),
留它的意义只剩排障时做对照。代码里以 `SXCL_AUTH_COMMUNITY_CLIENT_ID` 常量保留,不设成默认。

## 6. 令牌怎么落盘(安全存储)

**硬规矩:文件里绝不放明文 token。** 后端按平台自动挑,挑不到强后端就降级,并且**如实把降级路径与风险报出来**:

| 后端 | 平台 | 实现 | 强度与边界 |
| --- | --- | --- | --- |
| `dpapi` | Windows | CryptProtectData(带应用熵,CRYPTPROTECT_UI_FORBIDDEN) | 密钥由**当前用户**的登录凭据派生;换用户/换机器都解不开。以同一用户运行的其它程序仍可解 —— 这是 DPAPI 的既定边界 |
| `keychain` | macOS | SecItemAdd / SecItemCopyMatching / SecItemDelete(kSecClassGenericPassword) | 由系统钥匙串保管,受用户登录密码保护 |
| `libsecret` | Linux | **运行时 dlopen(libsecret-1.so.0)**(不引入链接期依赖) | 交给 GNOME Keyring 等;找不到就降级 |
| `file+key` | 全部(降级) | **0600 文件 + 本机派生密钥 + ChaCha20-Poly1305** | 见 6.2 |

`sxcl_auth_store_backend()` 报当前用的是哪个,`sxcl_auth_store_kind_note()` 报风险说明,
`sxcl-dl auth status` 会把两者直接打给用户看。

### 6.1 文件格式

```
  "SXCLAUTH"(8) | 版本(1) | 后端(1) | flags(2, LE) | 载荷长度(4, LE) | 载荷...
```

- 头部同时作为 AEAD 的**附加认证数据(AAD)**:改一个字节头就解密失败,而不是读出乱七八糟的东西。
- 降级路径的载荷 = nonce(12) || 密文 || tag(16),AEAD = **ChaCha20-Poly1305(RFC 8439)**。
- DPAPI 路径的载荷 = DPAPI 自己的 DATA_BLOB。

### 6.2 降级路径的密钥怎么来的(以及它到底挡得住什么)

```
  key = SHA256("SXCLAUTH|v1|machine-key" || SHA256(机器材料) || 随机盐(32B, 0600 文件))
  机器材料 = Windows: HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid + 用户名
             Linux:   /etc/machine-id + 用户名        macOS: 主机名 + 用户名
```

**它能挡**:把令牌文件拷到别的机器/别的用户下解不开;误提交进仓库也解不开(盐不在仓库里)。
**它挡不住**:同一台机器上、以**同一用户**运行的其它程序 —— 因为密钥必须能从本机材料重新算出来。
装好 DPAPI / Keychain / libsecret 的环境会自动走强后端,不会用这条。

### 6.3 落盘时机(这条是**实测踩出来的**)

**微软令牌一到手就立刻加密落盘**,哪怕后面某一跳失败。
理由:设备码流里用户亲手输一次码是**最贵**的操作;如果因为第 6 跳(应用没审批)失败就把 refresh token 丢掉,
用户要再输一次码 —— 第一版实现就是这么白扔了用户的一次登录。现在改成:

- `sxcl_auth_login()` 失败时也会把已经拿到的微软令牌留在 `session.ms` 里(有回归测试守住);
- CLI 在失败路径上照样保存,并明确告诉用户:修好后跑 `sxcl-dl auth refresh` 重试,**不用再输码**。

## 7. CLI 用法

```
sxcl-dl auth login   [--device-code] [--client-id ID] [--tenant T] [--no-browser]
                     [--wait MS] [--poll-ms MS] [--http-timeout MS]
                     [--token-file PATH] [--settings PATH]
sxcl-dl auth status  [--token-file PATH]
sxcl-dl auth refresh [--client-id ID] [--tenant T]
sxcl-dl auth logout  [--token-file PATH]
sxcl-dl auth bedrock [--token-file PATH]
sxcl-dl launch <版本名> <游戏目录> [--account] [--token-file PATH]
```

- `login`:默认走**授权码流 + PKCE + 环回**(自动开浏览器);`--device-code` 走设备码兜底。
  设备码会把 `user_code` / `verification_uri` / `expires_in` / `interval` 四项都打出来。
- `status`:看当前登录状态、加密后端、令牌前缀与过期时间。
- `refresh`:**免密**续期并重跑后半条链。
- `logout`:删掉加密令牌文件(幂等)。
- `bedrock`:用已存下的微软凭据跑基岩链(单独一条,不动 Java 段)。
- `launch --account`:用已登录的正版身份启动(与 `--offline <名字>` 并列,两者不能同时用)。
  它会把玩家名/uuid/accessToken/userType=msa 交给启动层,并支持 1.20.2+ 需要的 `${auth_xuid}` 与 `${clientid}` 占位符。

**输出纪律**:只打印令牌的前 6 位 + 字节数 + 过期时间(`sxcl_auth_mask_token`),**任何位置都不打印明文**。

## 8. 已知边界(别指望它做不到的事)

1. **Java 版与基岩版的权益互相独立**,不许拿一边推断另一边(两次购买、两套权益接口)。
2. **把 chain 送进官方基岩客户端,在安卓上基本做不到**:官方客户端用自己密钥库里的身份私钥签后续握手包,
   不接受外来的 chain 加我们的私钥。**我们只负责把链取回来**,不假装能替官方客户端登录。
   (本仓库基岩链的产出就是 chain 与身份公钥,供自研联机 / Rust 侧使用。)
3. **第 5 跳需要应用在 Mojang 那里有户口**:login_with_xbox 只接受登记过的 client_id,
   否则一律 HTTP 403 Invalid app registration(见 9.2)。这不是代码能绕过的,只能申请或用合规的既有应用。
4. 授权码流的环回服务需要**能监听 127.0.0.1**;受限环境不允许本地监听时请改用 `--device-code`,
   代码会给出明确提示(不是含糊失败)。
5. 设备码流的轮询总时长以微软给的 expires_in(通常 900 秒)为上限;超时如实报设备码已过期。
6. `file+key` 降级路径挡不住同机同用户的其它程序(见 6.2),这一点**会打给用户看**,不藏着。

## 9. 真链路实测记录(2026 年 2 月,本机 Windows)

### 9.1 跑通了什么(真实账号参与)

| 步骤 | 结果 |
| --- | --- |
| 1 设备码申请 POST /consumers/oauth2/v2.0/devicecode | **HTTP 200**,拿到 user_code / verification_uri / expires_in=900 / interval=5 |
| 2 用户输入码并同意 | 轮询按 interval 进行,authorization_pending 正确处理,最终拿到 token |
| 3 POST /consumers/oauth2/v2.0/token | **HTTP 200**,拿到 access_token + refresh_token(offline_access 生效) |
| 4 POST user.auth.xboxlive.com/user/authenticate | **HTTP 200**,拿到 XBL Token + uhs |
| 5 POST xsts.auth.xboxlive.com/xsts/authorize(中继方 rp://api.minecraftservices.com/) | **HTTP 200**,拿到 XSTS + uhs / xid |

所以那一项**未完成真人 + 真令牌启动**;入口、参数拼装、进程启动与日志解析已实现,并用离线令牌实测。

### 9.2 卡点:第 6 跳 403 Invalid app registration

```
POST https://api.minecraftservices.com/authentication/login_with_xbox
HTTP/1.1 403
{"path":"/authentication/login_with_xbox","errorType":"FORBIDDEN","error":"FORBIDDEN",
 "errorMessage":"Invalid app registration, see https://aka.ms/AppRegInfo for more information"}
```

**含义**:api.minecraftservices.com 只接受**在 Mojang 登记过**的 client_id。
未登记的应用,不管账号有没有买 Java 版,这一跳都是 403。这与账号问题/地区问题无关,是**应用户口**问题。

**两条路**:

- **A(已实测否定)**:用社区公共 id `00000000402b5328`. 实测它在 login.microsoftonline.com 上**不可用**,
  连第 1 步都过不去(详见 9.3)。**不要**把它当默认值。
- **B(推荐,长期正解)**:给 `aa4e81c8-f550-4720-bc51-c9b126f456d1` 申请 Minecraft API 资格(https://aka.ms/AppRegInfo)。

**拿到资格后的自助验证步骤(不用改代码、不用重新编译)**:

```
1) 用同一个 client_id 重跑:
     sxcl-dl auth login --device-code --client-id aa4e81c8-f550-4720-bc51-c9b126f456d1 --tenant consumers
   期望:第 6 跳从 403 变成 200,输出里出现
     Java 版:name=<玩家名> uuid=<uuid>   权益:拥有 Java 版权益(mcstore 条目数 2)
2) 如果之前登录过(令牌已加密落盘):直接
     sxcl-dl auth refresh
   即可 —— 不用让用户再输一次设备码。
3) 想连基岩一起验:
     sxcl-dl auth bedrock
   期望:chain 段数 >= 1;若返回 403 且正文提到没有权益,说明该账号确实没买基岩(与 Java 权益独立)。
4) 想直接用正版身份启动:
     sxcl-dl launch <版本名> <游戏目录> --account --verbose
   判据:日志里出现 Setting user: <name>,且没有 401 / Invalid token 一类鉴权错误。
```

### 9.3 历史端点说明(为什么 00000000402b5328 不可用;只读探测,不设默认)

该 id 是**老 Live Connect 时代的第一方 id**,只认旧端点。实测(只读探测,不改产品路径):

| 探测 | 结果 |
| --- | --- |
| GET https://login.live.com/oauth20_authorize.srf?client_id=00000000402b5328 | **HTTP 200**(页面正常给出 -> 旧端点认这个 id) |
| POST https://login.live.com/oauth20_token.srf(故意用错码) | **HTTP 400** invalid_grant:The provided value for the code parameter is not valid -> id 被接受,只是码不对 |
| POST https://login.live.com/oauth20_devicecode.srf | **HTTP 404**(旧端点**没有设备码流**) |
| POST https://login.microsoftonline.com/consumers/oauth2/v2.0/devicecode(对照) | **HTTP 400 AADSTS700016**(该目录里没有这个应用) |

结论:老 id 加老端点只支持交互式授权码流,**没有设备码**;而我们的产品路径固定在 login.microsoftonline.com。
因此它只剩排障对照的价值,我们**不改产品路径去绕合规**,而是走 9.2 的方案 B。

### 9.4 真实凭据的加密落盘(已实测)

- 默认令牌文件:%APPDATA%/SilentXCraftLauncher/auth/tokens.bin(CLI 的 `auth status` 会打出来);
- 本机后端:**dpapi**(`sxcl_auth_store_backend()` 报告;另有 Keychain / libsecret / file+key 三条路,见第 6 节);
- 证据(两个独立进程):
  1. 写:一份会话保存到文件后,文件头是 `53 58 43 4c 41 55 54 48 01 01 00 00 ...` = magic SXCLAUTH + 版本 1 + 后端 01(DPAPI);
     全文搜索令牌明文串 -> **搜不到**;
  2. 读:`sxcl-dl auth status --token-file <那个文件>` 能解出账号名/玩家名/过期时间(中文不乱码);
  3. 用:`sxcl-dl auth refresh --token-file <那个文件>` 会把文件里的 refresh token **真的发给微软**
     (探测用的假串得到 HTTP 400 AADSTS7000012,证明请求里用的就是落盘凭据,且**没有要求用户重新登录**)。

### 9.5 基岩链的实测结论

**待补(需要一份有效的微软令牌)**:第 6 跳失败使上一轮的 refresh token 丢失(缺陷已修,见 6.3),
拿到有效凭据后补上:

- XSTS(中继方 https://multiplayer.minecraft.net/) -> POST /authentication 的**状态码与原始响应**;
- 用**实测**回答基岩链是否也需要 Mojang 那道审批(第 6 跳的审批是 api.minecraftservices.com 的要求,
  基岩走的是另一个主机,预期不受同一限制 —— 但**以实测为准**,测出来之前不写死结论);
- 同时验证 refresh 免密续期(用真实 refresh token 换新 token)。
