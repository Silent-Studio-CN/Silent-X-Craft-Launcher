# 26 团队（好友 / 聊天）可行性：我们能碰到哪一层

> 用户设想：「玩家之间的加好友，实时聊天之类的」。
> 用户问：「官基有好友机制，JAVA 新版才引入。但是这些好像涉及 XBOX。我们能碰到吗？」

本文 = 查证结论 + 三条可选路线 + 各自代价。**没写的部分就是没查到，不猜。**

---

## 1 官方这套到底是什么（有出处的部分）

Java 版的 Friends List（新版引入）在 wiki 上是这么描述的（`https://minecraft.wiki/w/Friends_List`，2026-09-22 取）：

* 它是**游戏内的一个社交菜单**（overlay，两个页签：Friends / Requests），可以加/删好友、看在线状态；
* **加好友会同时在 Xbox 网络上发一次好友请求**：「The player can send a friend request to another player by entering their
  Java Edition profile name into the search box in the "Friends" tab, **which also sends a friend request on the Xbox network**」；
* 收到的请求「either in the Requests tab **or on the Xbox network**」都能处理；
* **聊天可见性由 Xbox 档案设置决定**：「Players that have their chat settings set to "Friends Only" on their Xbox profile
  see only chat messages from players if they are friends」；
* 好友之间可以**互相进对方的世界**：`Invite to game` 按钮 + **P2P**（「could join each other's online multiplayer worlds via Peer-to-Peer」）。

**结论**：Java 版的这一整套是 **Xbox 账号体系上的社交图谱 + 游戏自己的 P2P 会话**。
好友关系不在 Mojang 这边独立存在（至少在 wiki 的描述里是"同时也在 Xbox 上"），聊天是游戏内协议，不是某个 REST 接口。

## 2 我们能碰到什么

| 能力 | 能不能碰 | 依据 / 代价 |
| --- | --- | --- |
| **Xbox 好友列表 / 在线状态（只读）** | **能** | 我们登录时**已经拿到 XBL + XSTS**（微软 → XBL → XSTS → Minecraft 的那条链，`include/sxcl/auth.h` 里就有）；社区广泛使用 `profile.xboxlive.com` / `peoplehub.xboxlive.com` 这类端点读好友与 presence。**非官方文档**：随时可能变；涉及个人数据（要用户明确同意）；ToS 是灰区 |
| **游戏内那种实时聊天（Friends Only）** | **碰不到（不建议碰）** | 没有任何公开接口。Xbox 自己的消息通道（Xbox 客户端专用）没有对第三方开放；要发消息 = 逆向 + 随时挂 + ToS 风险。而且"游戏内聊天"发生在游戏的连接里，启动器不在那条链路上 |
| **好友之间进世界（P2P 邀请）** | **半能** | 邀请动作在**游戏里**；启动器能做的是"看到谁在线 + 一键把游戏拉起来并提示他"，真正的邀请仍由游戏发起 |
| **基岩版** | 同一套账号，情况类似 | 基岩的好友就是 Xbox 好友，多人走 Xbox Live 多人服务；第三方要"正式"接需要 Xbox Live 的应用注册 |

社区里确实有人在这条线上做东西（一个 npm 包 `@dendotdev/conch`、一个把好友列表与 P2P 玩法回移到旧版的 Mod `Friendlist & P2P Play Backport`），
说明**数据面是能通的**；但它们是"跟着改"的活，不是可以当成稳定契约的 API。

## 3 三条路线（建议 A+B，C 作为增强）

| 路线 | 内容 | 代价 | 风险 |
| --- | --- | --- | --- |
| **A. 只读 Xbox 社交** | 用我们已有的 XSTS 调 Xbox Live：好友列表 + 在线状态 + 点一下"启动并进他的世界"（提示玩家用游戏内邀请） | 3-6 天（网络层 + 一页 UI + 权限开关） | 非官方端点、会变；隐私（必须显式同意 + 可关闭） |
| **B. 自建好友 + 聊天**（**主线**） | 我们自己的服务：账号绑定、好友关系、消息（长连接或轮询）；与联机页那套"房间码 + 中继"共用一套会话 | 服务端 2-4 周（含部署与合规）+ 客户端 1-2 周 | 需要服务器与运维；但**完全可控**，跨 Java/基岩都能用 |
| **C. 混合** | A 只用来"发现"（谁在线），B 负责聊天/邀请；两条互不依赖 | 在 A+B 之上再加 2-3 天 | 同 A + B |

## 4 现在就定下来的事（写进代码）

* "团队"页**不再走 Xbox 官方接口** —— 该页按 **B 的骨架**做：好友列表 + 会话（先本地/空实现，接口留好）；
* A（Xbox 只读）**不默认开**：等用户明确要了再加，且必须在设置里显式同意；
* 这一条写进 `docs/25` §5（团队页的语义从"三选一"改成"好友 + 聊天，走自建"）。

## 5 还没查证 / 没读实现的部分（如实列出）

* Xbox Live 那几个端点**没有一个官方文档**对第三方开放；上面的"能碰"来自社区实践与公开讨论，没有官方承诺；
* Java 版好友服务**是否有 Mojang 侧接口**（比如 `api.minecraftservices.com` 下）我没有找到任何公开文档 —— 不敢断言"一定没有"；
* 基岩版的多人/Xbox Live 接口**需要什么凭据**没查（要不要 Xbox Live 的 app id）——真要做 A 的时候必须先查这一条；
* `@dendotdev/conch` 与那个回移 Mod 的**内部实现**没读（raw.githubusercontent 在本机被解析到非公网 IP，取不到）。
