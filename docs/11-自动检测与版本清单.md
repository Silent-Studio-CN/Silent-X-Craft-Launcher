## 0. 这一轮新增/扩展的 C API(签名 + 为什么)

### ① 游戏目录:`include/sxcl/paths.h`

```c
typedef enum sxcl_paths_os { SXCL_PATHS_OS_WINDOWS, SXCL_PATHS_OS_LINUX,
                             SXCL_PATHS_OS_MACOS, SXCL_PATHS_OS_ANDROID } sxcl_paths_os;
sxcl_paths_os sxcl_paths_current_os(void);
const char *sxcl_paths_os_name(sxcl_paths_os os);

typedef struct sxcl_paths_env {   /* 可注入,所以三个平台的规则都能在任何机器上验 */
    const char *app_data, *local_app_data, *user_home, *program_dir,
               *xdg_data_home, *android_files, *android_shared;
} sxcl_paths_env;
void sxcl_paths_env_capture(sxcl_paths_env_store *store);

typedef struct sxcl_paths_root {  /* 候选根:路径 + 标签 + 归属 + 优先级 + 要不要展开实例 */
    char path[..], label[..], owner[..], source[..];
    int priority, expand;
} sxcl_paths_root;

size_t sxcl_paths_roots(const sxcl_paths_env *, sxcl_paths_os, sxcl_paths_root *out, size_t cap);
size_t sxcl_paths_expand_roots(const sxcl_paths_root *in, size_t n,
                               sxcl_paths_root *out, size_t cap);
int  sxcl_paths_detect_ex(const sxcl_paths_env *, sxcl_paths_os, sxcl_game_folders *,
                          const char *configured_dir, char *err, size_t err_len);
int  sxcl_paths_marks(const char *path);                      /* 像不像 MC 目录的判据位掩码 */
int  sxcl_paths_marks_text(int marks, int versions, char *out, size_t out_len);
```

**为什么这么设计**(不是"自己发明",是三个具体问题逼出来的):

* `sxcl_paths_roots` 把候选表从 `sxcl_paths_detect` 里**拆出来**,因为候选表必须能
  **注入环境变量**:否则单测只能测本机那一个平台,Linux/macOS/安卓三套规则永远没人验证。
  这与 java 那边的 `sxcl_java_candidate_paths`/`sxcl_java_scan_roots` 是同一个套路。
* `priority` 是"已配置目录最高优先"的落点,也解决了"同一个目录被两个来源列到"时该显示谁。
  排序口径:**priority 降序 -> score 降序 -> 保持候选表原有先后**(稳定)。
* `expand` 是 MultiMC/Prism/CurseForge 这一家族逼出来的:它们的数据目录下是
  `instances/<名字>/{.minecraft,minecraft}`(CurseForge 用 `Instances`),
  真正的游戏目录在**下一层**。不展开 = 永远扫不到这些启动器的实例。
* `sxcl_paths_marks` 回答"**为什么**你说这个目录像 MC 目录":不是靠名字猜,而是实测
  `versions/`(数出几个版本)、`libraries/`、`assets/`、`launcher_profiles.json`、`logs/`。

### ② Java:`include/sxcl/launch.h` 第 1c 节

```c
typedef enum sxcl_java_run_verdict {
    SXCL_JAVA_RUN_OK, SXCL_JAVA_RUN_MISSING, SXCL_JAVA_RUN_DENIED, SXCL_JAVA_RUN_NOEXEC,
    SXCL_JAVA_RUN_NOT_EXECUTABLE, SXCL_JAVA_RUN_EXEC_FAILED, SXCL_JAVA_RUN_NOT_A_JRE,
    SXCL_JAVA_RUN_ARCH_MISMATCH, SXCL_JAVA_RUN_COUNT
} sxcl_java_run_verdict;
const char *sxcl_java_run_verdict_name/key/hint(sxcl_java_run_verdict);

typedef struct sxcl_java_installation {   /* 一个候选的**实测**结果 */
    sxcl_java_info info; sxcl_java_run_verdict verdict; int executed, priority;
    char source[24], owner[64], reason[192];
} sxcl_java_installation;
typedef struct sxcl_java_installations {
    sxcl_java_installation items[SXCL_JAVA_MAX_INSTALLS]; /* 32 */
    size_t count, usable, broken;
} sxcl_java_installations;

int  sxcl_java_exec_version(const char *java_exe_or_home, int timeout_ms, sxcl_java_info *out);
const char *sxcl_java_host_arch(void);
int  sxcl_java_binary_arch(const char *path, char *out, size_t out_len);
size_t sxcl_java_detect(const sxcl_java_env *, sxcl_java_os, int timeout_ms,
                        sxcl_java_installations *out);
```

**为什么要 `exec_version` 这一层**:现有 `sxcl_java_inspect/discover` 读的是
`<home>/release` 这份**文本**。文本可以是从别处拷来的、可以是 32 位换成 64 位忘了改的、
目录名也可能写着 jdk-21 而里面是别的版本。要回答"这个二进制在**这台机器上**到底能不能跑、
跑起来是哪个版本",唯一的办法就是真的起一次进程 —— 本层做这件事。

**为什么 `binary_arch` 单独存在**:架构不符要在**起进程之前**判出来。安卓上 exec 失败的
错误信息往往只是一句 "can't execute",看不出是架构问题;读 ELF/PE/Mach-O 文件头则一眼看穿,
也不用白等一个注定失败、可能超时的进程。

**为什么 `detect` 把"不可用"的也返回**:需求原文是"分类给出不可用原因,别静默丢弃"。
`count` 是全部(含不可用),`usable`/`broken` 是计数;界面据此显示
"检测到但用不了:沙箱拒绝/共享存储不能执行/没有执行位/不是 Java/架构不符/跑不起来"。
唯一不进结果的是 `MISSING`(那个位置没有东西)—— PATH 里每个目录都会产生一条,
全收下会把上限撑满,真正存在的反而被截掉(见 §2.4 的实测)。

### 2.3 安卓:别的启动器的 JRE **用不了**(已确立的事实,写进文档别再推翻)

两道锁同时锁死(设备实测,见 docs/08 第 14 节):

* **沙箱**:每个应用的私有目录属于各自的 uid,SELinux 域也不同。别的应用去
  `stat/opendir` 直接 `EACCES` -> 结论 **`denied`**;
* **noexec**:共享存储(`/storage/emulated`)是 fuse 挂载、带 `noexec`,即使文件有 `+x`
  也起不了进程 -> 结论 **`noexec`**。

所以安卓上**只有我们自己私有目录里的文件是"我们自己的"—— 但应用自己 exec 不了它**
(2026-09-21 更正:真机上应用进程 exec `files/runtime/**/bin/java` 被 SELinux 拒
`execute_no_trans`,`permissive=0`;`run-as` 会话能跑是 `runas_app` 域的假象。
证据原文见 `docs/18-安卓起JVM的最小落地.md` §4.2)。要起 JVM 只能**进程内 dlopen
`libjli.so` + `JLI_Launch`**。检测结果里这些候选会被标成
"检测到但不可用"(带原因与下一步),并且引导走设置页的**「下载 Java」**
(`sxcl_java_runtime_install`,官方 JRE 组件、逐文件 sha1 强校验、装到应用私有目录)。

### 2.4 这一轮因此挖出的两个真 bug(已修)

1. **Windows 上 PATH 被按 `:` 切**。老代码:
   `while (*end && *end != ';' && *end != ':')` —— 盘符被切断,候选表里冒出 24 条
   `C\java.exe` / `\Program Files\...\java.exe` 这种**假路径**(实测日志为证)。
   改成按目标平台:Windows 只认 `'?'`(`;`),POSIX 只认 `:`,并去掉 PATH 项两端的引号。
2. **假候选把上限撑满**。`SXCL_JAVA_MAX_INSTALLS`(24)被 24 条"不在"的噪声占满,
   真正存在的 `jre-legacy`/`jdk26` **根本没被实测**(它们的 verdict 是空的)。
   改成"不在"不进结果(与界面口径一致),上限提到 32。修完三条真 Java 全部拿到实测结论。

另:`sxcl_java_detect` 每个候选要起一次进程(几百毫秒),而设置页 `refresh()` 在
"主题/语言变了"时会连调 3 次 —— 界面层加了按"候选集合"为键的缓存,不再重复起进程。

### 2.5 测试(不联网、不要求机器上装了 JDK,但**真的起进程**)

`tests/java_finder_fixture.c` 是一个"冒充 java"的极小可执行文件:按**自己的文件名**决定
行为(`notjre` -> 打印一段不是 Java 的东西;`silent` -> 退出码 127 且无输出;其它 -> 打印
Temurin 21 的 `java -version` 横幅到 stderr)。`tests/java_finder_test.c` 通过
ctest 拿到它的绝对路径,复制成夹具树里的 `<home>/bin/java[.exe]`,然后:

* 断言 `sxcl_java_exec_version` **真的跑起来**并解析出 `21 / Eclipse Adoptium / 64 位`;
* 真跑不起来的两种情形分别落到 `not_a_jre` / `exec_failed`;
* 架构不符(往夹具里写一段 arm64 的 ELF 头)落到 `arch_mismatch` 且**不去执行**;
* 全链路 `sxcl_java_detect` 的来源优先级排序、`usable`/`broken` 计数。

## 3. ③ 版本清单取数链(闭环)

### 3.1 UI:两条数据来源,分开呈现

`src/ui/pages/versions_page.cpp`:

* **远端清单**:`sxcl_http_get_text` 双路(官方 `piston-meta.mojang.com` -> BMCLAPI 镜像,
  镜像 URL 由 `sxcl_manifest_mirror_url` 生成)-> `sxcl_json_parse` ->
  `sxcl_version_list_build`;成功后顺手写
  `%APPDATA%/SilentXCraftLauncher/cache/version_manifest_v2.json`。
* **本地已安装**:`sxcl_instance_scan`(带加载器标签 "Forge 47.2.0" 与 problem 人话)。
* 两者**只在行上相遇**:已安装的版本在对应行打"已安装"标记 + 加载器小标签;
  `m_all`(列表内容)永远是清单,或(且仅在清单失败时)本地已安装那几条,并且状态行**明说**
  是哪种。
* `SXCL_UI_MANIFEST=<json>` 仍是最高的**显式入口**(验收/离线复现);
  远端不通才退本地缓存,并且弹一条 Warning 说"用的是上次缓存下来的清单"。

**三态(别再合并,这是踩过的坑)**:

| 情形 | 状态行 | 列表 |
|---|---|---|
| 清单拿到了 | `共 N 个版本，已安装 M 个 | 当前显示 K 个 | <加载器汇总>` | 远端清单 |
| 清单失败 + 本地装了 | `版本清单加载失败：<真实原因> · 下面列出的是**本地已安装**的 M 个版本，不是远端清单` + InfoBar.error | 本地已安装 |
| 清单失败 + 本地没装 | `版本清单加载失败：<真实原因> · 本地也没有已安装的版本(全新设备属于正常情况,去「下载」页装一个即可)` + InfoBar.error | 空 |

目录里就是启动层要的东西:`versions/1.0/1.0.json`(8186 字节)+`versions/1.0/1.0.jar`
(2362837 字节)。启动层的 `sxcl_instance_read_json` 读的正是这个位置(PCL 式兜底:
同名优先,否则取目录里任意含 `mainClass+type+id` 的 JSON),所以**不需要手工补文件**。

### 3.4 这一轮因此挖出的真 bug:同一个文件被排了两次队

官方 `1.0` 的版本 JSON 里 `net.java.jinput:jinput-platform:2.0.5` **被列了两遍**
(实测 `[regex]::Matches($json,'"name": "net.java.jinput:jinput-platform:2.0.5"')` = **2**),
于是下载计划里出现两个 `dest` 完全相同的任务 -> 两个工作线程同时开同一个
`<dest>.part` -> 第二个拿到共享冲突,引擎报
`无法写入 ...jinput-platform-2.0.5-natives-windows.jar.part`:

```
第一批完成 13 个, 失败 1 个
```

删掉文件重跑**可复现**。修法:`sxcl_version_plan` 里加一个**目标路径去重集**
(FNV-1a + 开放寻址,16384 槽),`plan_add` 遇到已经排过的 `dest` 直接跳过
(装不下时退化成不去重:不会错,只是可能重复下载)。修后同样是全新目录:
`第一批完成 13 个, 失败 0 个`。

### 3.5 双路清单(CLI 与 UI 同一套核心库)

* `kManifestUrl`(官方)+`kManifestMirrorUrl`(BMCLAPI):`sxcl_task.urls[1]` = 镜像,
  官方不通时引擎自己换路(每条路重试 `retry_per_source` 次)。
* 版本 JSON 同样两条路;`sxcl_version_plan_add_mirror` 给计划里**每个**还没有第二路的任务
  (客户端 jar / 依赖库 / natives)补镜像 —— 只配清单镜像是没用的。
* 用法:`sxcl-dl version <id> <dir> [--mirror URL] [--skip-assets] [--asset-mirror URL]`。
  `--mirror` 在这里表示"镜像根",不传就用 BMCLAPI。

### 5.3 ⚠ 已知限制:真机验收**待解锁**(不是"应该能行",是当前做不了)

设备现在**处于锁屏状态**(keyguard + 有锁屏凭据)。实测表现:`am start` 能把 Activity 拉起来,
但界面被挡在锁屏之后,**截图全黑**,logcat 里也拿不到设置页跑起来的那些行 —— 也就是说

按纪律:**不猜、不用 `input swipe/tap` 绕过锁屏**(那会污染结论,而且另一路代理正在等解锁后
先量修复前的基线,不能抢设备)。解锁后按下面两条命令即可完成取证(无需改代码):

```powershell
# 1) 装机 + 授权前后对比 + logcat + 截图(脚本已存在,设备参数就是这台)
pwsh -File build\_android\scripts\android_detect_evidence.ps1 -Dev 192.168.200.164:5555

# 2) 单看这几行就是我们这一轮加的机器可读输出
adb -s 192.168.200.164:5555 logcat -d | Select-String 'gamedir-detect|gamedir-probe|java-discover|版本页'
```

要看的结论(与桌面同一套口径):

* `gamedir-detect`:授权**前**共享存储候选应为 `被沙箱挡住`(`denied`);
  `appops set <pkg> MANAGE_EXTERNAL_STORAGE allow` 之后同一批候选应能读到并数出版本数;
* `java-discover`:本应用私有目录里的那份 `usable=1`(如果用户下过 Java);
  别的启动器(HMCL/FCL/PojavLauncher)的私有目录应报 **`denied`**,共享存储上的应报 **`noexec`**
  —— 这正是"检测到但不可用,引导走「下载 Java」"那条产品行为;
* `版本页`:清单 `OK` 且版本数 > 0(安卓同样走核心库双路),本地已安装单独计数。

## 6. 已知限制与没做的事(如实写)

1. **安卓真机验收待解锁**(见 §5.3)。桌面三平台(Windows 实测;Linux/macOS 的规则由
   `sxcl_paths_roots`/`sxcl_java_scan_roots` 的可注入 env 单测覆盖,**不是**在真机上跑过)。
2. `MultiMC/Prism/CurseForge/ATLauncher` 的候选**本机没有装**,所以"能扫到实例目录"
   这一条是**夹具实测**(tests/paths_roots_test.c 造了 `instances/MyPack/minecraft` 与
   `Instances/Pack/minecraft` 两棵树),不是真机装上这些启动器后跑的。
3. `sxcl_paths_marks` 的 `logs/` 判据只用于展示,不参与排序(排序仍是
   priority -> versions*10 + assets*5 + profiles*2,与 Python folders.py 的 score 一致)。
4. 清单/版本 JSON/依赖库的第二路走 BMCLAPI 的**前缀映射**;镜像站若改了目录结构
   (例如 `/maven` 改名),映射表要跟着改(一处:`sxcl_manifest_mirror_url`)。
5. `sxcl_java_detect` 一次最多返回 `SXCL_JAVA_MAX_INSTALLS`(32)条;"不在"的候选不进结果,
   所以它**不是**"扫过哪些地方"的完整报告 —— 那个用途请用
   `sxcl_java_probe_android` / `sxcl_paths_probe_android`(安卓那份逐条给人话)。
6. 版本页的"已安装"标记来自 `sxcl_instance_scan`,它按 PCL 口径(目录里有可用版本 JSON 就算);
   `sxcl_python` 版 `installed.py` 是"jar + json 都齐全"的更严口径,两者对
   加载器实例(没有自己的 jar)的结论不同 —— C 版与扫描层保持一致,这是**有意**的。
