# 15 · 下载源(官方 / BMCLAPI)与"镜像优先"

本文记录"设置里切了下载源,游戏文件还是走官方"这条缺陷在**核心库**里的修法、真实证据与坑。
所有命令都是在 `D:\SilentStudio\prog\Silent-X-Craft-Launcher - C` 下真实跑出来的,输出原文照抄。

相关文件:`include/sxcl/manifest.h`、`src/services/metadata/manifest.c`、`include/sxcl/install.h`、
`src/services/install/install.c`、`tools/sxcl-dl/main.c`、`src/net/transport_qt.cpp`、
`tests/manifest_test.c`、`tests/install_test.c`。

## 0. 问题

`download.source = bmclapi` 以前只作用于**清单**(版本列表);游戏文件(版本 JSON / 客户端 jar /
依赖库 / 资源对象 / 加载器安装包)的计划里永远是"官方 `urls[0]`、镜像 `urls[1]`",
镜像只有官方彻底失败才用得上 —— 用户看到的还是"官方慢 / 官方不通"。`download.source` 在核心库里
从来没有人读过。

## 1. 新增的 C API(签名 + 为什么)

```c
/* include/sxcl/manifest.h */
int sxcl_version_plan_prefer_mirror(sxcl_version_plan *plan);
```

- 语义:遍历计划里所有任务,把 `urls[0]` / `urls[1]` **对调**;没有第二候选的任务不动。
  返回被调换的任务数,< 0 = 参数错误(plan 为空)。
- 为什么是"对调"而不是"重排":plan 接管了这些 URL 字符串的生命周期(`plan->owned`),
  换指针就够了,不复制、不释放。
- **只应调用一次**:它只做一次交换、不记状态,调两次就换回"官方在前"。这条写进了头文件注释,
  测试里也顺手钉住了(见 §5)。
- 为什么需要它:资源对象是**后追加**的一批(要先下资源索引才能展开),
  而"镜像优先"必须是每一批各自在下载前定好顺序 —— 见 §2。

## 2. install.c 的接线(为什么一批一次)

`sxcl_install_plan` 增加了 `int prefer_mirror`(放在 `mirror_base` 旁边):

```c
int prefer_mirror;  /* 1 = 镜像优先:镜像排第一、官方作第二候选(不通自动切回);0 = 官方优先 */
```

`mirror_base` 为空且 `prefer_mirror=1` 时用 `SXCL_MIRROR_BMCLAPI_BASE`(默认 bmclapi)。

装配与下载是交错的(阶段表:版本 JSON → 客户端 jar → 依赖库 → 资源索引 → 资源对象),
所以顺序分两处、各定一次,而不是"最后统一换一次":

| 批次 | 位置 | 做法 |
| --- | --- | --- |
| 版本清单(fetch_text) | `stage_manifest` | `prefer_mirror=1` 时先取镜像、失败再取官方 |
| 版本 JSON | `stage_version_json` | 镜像映射出来后按开关放到 `urls[0]` |
| 客户端 jar / 依赖库 / 资源索引 | `stage_version_json` 计划建好后 | `sxcl_version_plan_add_mirror` 补第二路 → `sxcl_version_plan_prefer_mirror`(**只此一次**) |
| 资源对象 | `stage_asset_objects` | 追加时直接对调参数(base=镜像的 `/assets`,第二候选=官方 CDN);**不能**再调一次 prefer_mirror |
| 加载器安装包 | `stage_loader_installer` | 认得出的 URL 才补镜像,认不出就只有官方一条路(不造假 URL) |

`mirror_base` 是"镜像根"(与 `add_mirror` 一个口径,如 `https://bmclapi2.bangbang93.com`),
资源对象在它下面的 `/assets`;调用方已经写成 `.../assets` 时不再拼一层。

## 3. 命令行 `--source`

```
sxcl-dl version <版本号|latest> <游戏目录> [--source bmclapi|mojang|auto] [...]
  └ --source 决定哪条路排第一(默认 bmclapi):bmclapi/auto = 镜像优先、官方作第二候选
    (镜像不通自动切官方);mojang = 官方优先
```

默认 **bmclapi**(与设置页默认一致)。`--verbose` 下每个文件的完成行会打出
**真正成功的候选下标与它的 URL**(`来源 #N <url>`),这样"镜像排第几"是日志里的直接证据。

## 4. 顺带修掉的真机缺陷:Qt 传输不跟 302(BMCLAPI 全是 302)

第一版改完做真机验证时,`来源 #` 几乎全是 **1(官方)** —— 说明镜像那条路每次都被跳过。
用 `SXCL_NET_DEBUG=1` 看原始响应:

```
QT https://bmclapi2.bangbang93.com/mc/game/version_manifest_v2.json (h2=1 range=-1) -> 302
  location: https://14.749333.xyz:443/download/b7c75...?...&name=version_manifest_v2.json
```

BMCLAPI 对**每个文件**都先 302 到预签名 URL 再 200(curl 实测 2 跳)。
`src/net/transport_qt.cpp` 的等待循环"一看到状态码就跳出",拿到的是第一跳的 302,
于是镜像永远算"HTTP 302 失败"、每次都回落官方 —— 镜像排第一等于白排。
修法:301/302/303/307/308 且 Qt 还在跟(reply 未结束)时**继续等**,直到最终状态或超时。

## 6. 没做的

- `sxcl-dl` 没有 `install` 子命令,所以 install.c 那条路没有命令行端到端;
  它的接线由 `tests/install_test.c` 的假 io 断言(12 项)覆盖。

## 7. 慢到离谱的源：不再"掉头就走"，也不再"干等到天荒地老"（2026-09-22 晚，真机）

### 7.1 起因：Quilt 的安装器只有一家在托管，而它慢得不正常

Quilt 的产物**只**在 maven.quiltmc.org 上（本轮实测）：

| 候选 | 结果 |
|---|---|
| maven.quiltmc.org/.../quilt-installer-0.15.1.jar | 200，Content-Length: 8734533 |
| bmclapi2.bangbang93.com/maven/org/quiltmc/... | **404**（BMCLAPI 的 maven 代理没有 Quilt） |
| repo1.maven.org/maven2/org/quiltmc/... | **404**（Quilt 不发 Maven Central） |

同一个文件用系统 curl 量（2026-09-22 18:0x，本机网络）：

```$ curl -sS -o NUL --max-time 30 -w "bytes=%{size_download} speed=%{speed_download}" <上面那个 jar>
code=200 bytes=983040 speed=32755      # 30 秒只拿到 0.94MB ≈ 32.7KB/s，全部要 ~4.5 分钟
```
注意它**不是一直这么慢**：同一小时里同一台机器另外两次取样是 0.2~0.4MB/s，也有过
"连上以后一个字节都不来"的时候。这类源最难受的地方不是慢，是**不可预测**。

### 7.2 问题一：为一个"没履历"的备选，把正在出数据的源赶走了

引擎原有规则（与 Python 版一致）：某个候选在 8 秒宽限后平均速度低于 512KB/s，
而**后面还有别的候选**，就"换路续传"。这条规则在"官方 20KB/s、镜像 2MB/s"的常规场景里
是好事 —— 但在 Quilt 这种"唯一能出数据的源很慢、备选根本是死的"场景里是**灾难**：

`
8.7MB 的安装器，官方 32KB/s -> 8 秒后换路 -> 镜像 404 -> 本轮结束 -> 任务失败
`

真机症状（改之前）：下载停在 **1.19MB**，.part.json 记着 `written=1192768`，
进程 CPU 0.09s、**9 分钟零进展**，界面就那样一直显示"正在下载"。

**改法**（`src/core/dl/engine.c`）：

* `better_live_source()` 取代原来的"后面还有没有候选"：只有备选**没被判死**
  且**失败次数不超过**当前这一路（`fails <= 当前`）时才掉头。
  两边都没失败过 = 值得赌一次（常规场景照旧受益）；备选先失败过一次，
  就不再为它掉头 —— **慢 > 失败**；
* 候选**多轮**走（`SXCL_SOURCE_ROUNDS = 8`）：一轮结束只要**有进展**就再来一轮，
  每轮按最新的死活记录重排名次（判死的源排到最后、不删）。一轮下来零进展才认输。

### 7.3 问题二：连接还在、一个字节都不来 —— 没有停滞判据就会永久挂住

Qt 传输的"取正文"循环（`transport_qt.cpp` 的 `qtRead`）原来只判
"有数据 / 读完 / 出错 / 取消"，**没有"多久没数据就算死"**。网络一停摆，它就一直转：

`
进程 CPU 累计 0.09s、线程全在 Wait、有一根 ESTABLISHED 到 Cloudflare:443、
.part 九分钟一个字节没动 —— 而界面还在"正在下载"
`

**改法**：给每个响应体配一个**停滞看门狗**（`QtBody::lastData/stallMs`）：
请求超时的 2 倍（引擎给 30s -> 60s）内一个字节都没到，就 `abort()` 掉这次尝试、
报 `SXCL_NET_ERR_IO`。引擎按"传输中断"处理：**保留已下部分**，换路或原路续传。
（60 秒是有意的宽松值：慢到 32KB/s 的源每 1~2 秒也会来一批字节，60 秒没动静才是真死。）

**顺带查了 CLI 退出时那行 `QWaitCondition: Destroyed while threads are still waiting`（结论：没修掉）**：
先怀疑是 Qt 全局线程池（域名解析跑在上面）静态析构时还有等待线程，于是加了
`sxcl_transport_qt_drain()` 并在两处调用（transport 销毁处、CLI 退出前）。
**实测：告警照旧**（`sxcl-dl get` 与 `mods search` 都复现）—— 它来自 Qt 自己更深一层的收尾，
**不是我们的线程泄漏**：引擎 `sxcl_engine_run` 返回前 `sxcl_thread_join` 了所有工作线程，
进程 rc=0、CPU 与线程数都正常。所以这条老实记成「外观问题，未解决」；
真要消掉得连同 QCoreApplication 一起规范析构，而我们的 QCoreApplication 是**故意不释放**的进程级单例。

同一条命令在改之前是"1.19MB 处停死、九分钟零进展、最后整条失败"。

### 7.5 又试了分片：`--conn 8` 能快一阵，但源站对整条 IP 限速（2026-09-22 18:32~18:39）

为了不把「慢」变成「拿不到」，给 CLI 加了 `--conn N`（单文件分片数；门槛是文件 ≥4MB 且每片 ≥1MB，
见 `engine.h` 的 `SXCL_SEGMENT_MIN_*`）。慢源单连接只有几 KB/s 时，分片是唯一能自救的杠杆。

```
$ sxcl-dl get <quilt-installer 官方 URL> <%TEMP%>/sxcl-quilt/quilt-installer-0.15.1.jar
      --sha1 e4c4e80c91c94d999ffe3468ec2043792b841051 --size 8734533 --conn 8 --mirror <404 那条>
18:32:40 起跑
  [ 32.7%] ... 2.72 MB  0.02 MB/s      # 前 45 秒拿到 2.5MB ≈ 55KB/s（比单连接快一个量级）
  [ 40.9%] ... 3.40 MB  0.00 MB/s      # 之后 5 分钟只再拿到 0.67MB（≈2KB/s），停在 40.9%
```

**结论（明说）**：这家源对本机网络**不可用** —— 它是「先给你快一阵、然后按整条 IP 掐」的形态，
分片也救不回来。8.7MB 的安装器拿不到，所以 B7 的「安装 + 启动」e2e **依然没有真机证据**。
`--conn` 这个参数本身留着（对其它慢源是真有用的杠杆，也让「分片」这条代码路径第一次有了 CLI 入口）。
