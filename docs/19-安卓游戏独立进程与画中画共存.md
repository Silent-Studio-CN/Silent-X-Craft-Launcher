# 19. 安卓:游戏独立进程(:game)+ 启动器画中画共存(架构落地)

> 本轮**只打通架构**:两个进程、通道、画中画共存、结束游戏只结束游戏。
> **没有接游戏主类**(那一步等 JRE 包到位);代码里没有任何写死的 JRE 路径、不下载任何东西。
> 用户 2026-09-21 拍板原话:"那我选 B。画中画我们实践过。" —— B 就是本文这一套摆法。
>
> 本文同时是"游戏运行器"**边界接口**的定义(§3)与**将来拆成两个 APK 的接口草案**(§7)。

## 0. 结论(一句话)

游戏的 Activity 声明在 `android:process=":game"` 里(自己一个进程、自己一个窗口、自己的
SurfaceView);两个进程之间只有一条**本地 socket 通道**(主进程监听、游戏进程 connect);
拉起顺序是"**游戏先起(启动器还在前台)-> 游戏窗口就绪后把启动器拉回前台进画中画**"
(§2 说明为什么不能反过来);"结束游戏" = 主进程在通道上发 `END`,游戏进程有序收尾
(flush 日志 + 写退出记录)后**只结束 :game 这一个进程**;真机读数在 §5。

## 1. 摆法

    ┌────────────────────────────┐   本地 socket(AF_UNIX 抽象名)   ┌──────────────────────────┐
    │ 主进程 com.silentstudio.sxcl │ ──────────────────────────────▶ │ :game 进程                │
    │  SxclActivity(Qt / 画中画)   │  主->游戏:END                    │  GameActivity(SurfaceView)│
    │  GameHost(界面适配层)        │  游戏->主:HELLO/LOG/STATE/PING/   │  sxcl_game.c(通道 + 日志)│

    └────────────────────────────┘                                  │  sxcl_jre_bootstrap.c    │
                 ▲                                                   │  └─ 核心库 sxcl/jvm.h     │
                 │ 画中画(pinned task,浮在游戏之上)                    └──────────────────────────┘
            游戏全屏(task affinity = ...game)

## 2. 拉起顺序:**被系统规则逼出来的**,不是偏好

### 2.1 死路:"启动器先进画中画,再去起游戏"

直觉上应该"先让启动器进画中画(保住可见),再拉游戏"。真机(Android 15/16 级 ROM,
targetSdk 34)实测**被系统直接拒绝**,而且 `startActivity` **不抛异常**、静默失败 ——
只有看系统日志才知道。原文(192.168.200.164:5555,2026-09-21 20:28:06):

    E ActivityTaskManager: Background activity launch blocked! goo.gle/android-bal
      [callingPackage: com.silentstudio.sxcl; callingPackageTargetSdk: 34; callingUid: 10170;
       callingPid: 7724; appSwitchState: 2;
       callingUidHasVisibleActivity: true;            <- 我们确实有可见活动……
       callingUidHasVisibleNotPinnedActivity: false;  <- ……但它是 pinned(画中画),不算数
       callingUidHasNonAppVisibleWindow: false;
       callingUidProcState: TOP; intent: Intent { flg=0x10000000 cmp=com.silentstudio.sxcl/.GameActivity }]
    E ActivityTaskManager: Abort background activity starts from 10170
    I ActivityTaskManager: START u0 {cmp=com.silentstudio.sxcl/.GameActivity} from uid 10170
      (BAL_BLOCK) result code=102

读法:**画中画里的活动发起新活动 = 后台活动启动(BAL)**,系统一律拒(result code=102),
而我们的代码只看到"startActivity 返回了",于是 `:game` 进程根本没起来。
(能解开这条的钥匙只有"非 pinned 的可见活动"或"非应用可见窗口"—— 后者就是
SYSTEM_ALERT_WINDOW 悬浮窗,需要用户授权,不做默认路径。)

### 2.2 现在这一套:游戏先起,再由游戏把启动器请回画中画

1. `GameHost.requestStart()`:`openChannel(spec)`(§B)先在**主进程**里把本地 socket 监听
   建好、会话目录建好(游戏出生时监听必须已经在);
2. 启动器**此刻还是前台(可见、非 pinned)** -> `startActivity(GameActivity)` —— **允许**;
3. 游戏窗口就绪 -> **握手**(避免"已经在画中画里还被再拉出来一次",那会把游戏窗口打断):
   运行器在通道上发 `PIP?`,**主进程**回答 `PIP need=0|1`(`need = !isInFloating()` ——
   画中画状态只有主进程知道,静态字段各进程各一份)。`need=1` 时运行器才(作为前台的一侧)
   发起 `startActivity(SxclActivity, REORDER_TO_FRONT|SINGLE_TOP|NEW_TASK + makeLaunchIntoPip)`
   并带 `sxclRequestPip=1`;系统若不吃 launchIntoPip 也不要紧,启动器回前台后在
   `onNewIntent`(已在前台时没有 onResume)或 `onResume`(被拉回前台时)里调
   `enterFloating()`(**复用最大化键那条画中画实现**,失败重试两次并如实记日志);
4. 结果:游戏全屏在下、启动器画中画在上;游戏进程不因画中画受任何影响(pinned 窗口不构成遮挡,
   游戏活动保持 resumed)。
5. 兜底:20s 内没收到运行器的画中画请求,主进程**如实记一行**"启动器此刻不在可见处",
   不做假动作。
6. 如实说明一处取舍:spec 里的 `launcherPip` 目前运行器**固定会问一次**("要不要进画中画"),
   由主进程按 `need` 决定 —— 也就是说这个开关暂时不会被用来"完全禁止画中画"。

画中画里的出口仍然是那个原生按钮「回到启动器」(挂在窗口 decor 上,零权限,点它 = `exitFloating()`)。

## 3. "游戏运行器"边界接口(为将来拆成独立 APK 留的口子)

### 3.1 输入:`GameHost.GameLaunchSpec`(android/java/com/silentstudio/sxcl/GameHost.java §A 段)

| 字段 | 含义 | 现在怎么用 |
|---|---|---|
| `jreHome` | JRE 根目录 | 交给核心库 -> `-Djava.home` + dlopen libjli |
| `classpath` | 游戏 classpath | -> `-cp` |
| `nativesDir` | natives 目录 | -> `-Djava.library.path`(默认填 APK 的 nativeLibraryDir) |
| `gameDir` | 游戏目录 | -> `-Duser.dir` |
| `jvmArgs` | JVM 参数(空格分隔) | 主类之前的 argv |
| `gameArgs` | 游戏参数 | 主类之后的 argv |
| `mainClass` | 主类 | 本轮**不接**,为空时跑自检参数 |
| `renderer` | 渲染器 | 只进边界与日志:**渲染层本轮没接**(不假装有) |
| `sessionId` / `socketName` / `sessionDir` | 会话与通道 | 名字空间会合点 + 日志/退出记录落盘处 |
| `crashMode` | 崩溃注入(验收用) | 0 关 / 1 abort / 2 SIGTERM / 3 SIGKILL |
| `launcherPip` | 窗口就绪后请启动器进画中画 | 为什么必须由运行器发起见 §2.1 |

字段一律 String/int(不用 Parcelable):换传输介质(Intent extras -> Binder/传 fd)时不用改数据结构。

### 3.2 输出:日志流 / PID / 退出码或信号 / 结束命令

同一份 `GameHost.java` 里切成三段,**缝切在同一个文件里,不另立包/层**:

| 段 | 内容 | 有没有 UI 依赖 |
|---|---|---|
| §A 边界契约 | `GameLaunchSpec` + 协议动词 + 字段读法 + `Listener` 回调 | 无(只有 `Bundle` 当传输介质) |
| §B 运行器通道 | `openChannel/stopChannel/stateLine` + 接受连接/逐行解析/退出码与信号回收/状态机 | **无**:没有 Activity/View/画中画/Intent,连 Context 都没有(会话目录由 spec 给绝对路径) |
| §C 启动器适配 | `attach/requestStart/startGameActivity/onPipChanged/endGame` | 有(Context/Intent/画中画时序),只有这一段有 |

    // §B(零 UI)
    String  openChannel(GameLaunchSpec spec, Listener listener);  // 建会话 + 监听通道
    boolean stopChannel();                                       // 发 END(唯一控制命令)
    String  stateLine();
    // §A 事件
    interface Listener { void onLog(String); void onPid(int, String);
                         void onExit(int code, int signal, String reason, String source);
                         void onState(String); }

### 3.3 协议(行文本 + `key=value`,`GameHost.java` §A 段是唯一定义处)

    A -> B : END | PING?                     (END 是唯一的控制命令)
    B -> A : HELLO pid=N proc=<进程名> session=<id> chan=0|1 java=present|absent
             READY dir=... nativelib=... mainclass=... classpath=... gamedir=... renderer=...
             STATE ...            LOG <一行>            PING pid=N n=<计数>
             EXIT code=N signal=N reason=command|jvm-returned|body-returned
             SIG signal=N code=128+N      (崩溃兜底:先发这条,再 _exit(128+N))
             BYE
    B -> A : PIP?                        (窗口就绪;要不要把启动器拉回前台进画中画?)
    A -> B : PIP need=0|1                (主进程按自己的画中画状态回答)

### 3.4 异常断开(三种情况,都报事实、不猜)

1. **运行器自己崩**(ABRT/BUS/ILL/FPE/TERM/INT,可捕获):崩溃兜底(pipe + 看门线程)在
   `_exit(128+sig)` **之前**把 `SIG signal=N code=128+N` 用裸 `send()`/`write()` 写进通道
   **并且**写进**预先打开**的退出记录文件(`<session>/exit.txt`;崩溃路径不 malloc、不 open、不加锁)。
2. **被 kill -9 / OOM 杀**:信号不可捕获,通道直接 EOF。主进程按"EOF + 没有退出记录 +
   `/proc/<pid>` 消失"报 `killed`,并在日志里明说 **退出码/信号从进程外面不可观测** ——
   我们不是它的父进程,`waitpid`/`pidfd` 都拿不到退出状态,所以**不编数字**。
3. **主进程先没了**:运行器 `send()` 失败只把通道置灰,日志照旧写自己的文件、logcat 照旧,
   **游戏继续跑** —— 通道不是游戏的前提。

日志三条出口:运行器自己的 `<session>/game.log`(flush+fsync)、通道(主进程转 logcat tag `sxcl`)、
logcat tag `sxcl-game`。主进程每次状态变化另落一份 `<session>/host-state.txt`(`run-as` 就能读)。

## 5. 结束游戏 = 只结束游戏(逐条)

1. 主进程 `GameHost.endGame()`(§B `stopChannel()`)在通道上写 `END`;
2. 运行器 `chan_reader` 收到 `END` -> `game_request_stop("command")`:
   ① `sxcl_jre_request_shutdown()`(有 JVM 才做事;没有 JVM 返回 0,走 flush 路径)
   ② `game_flush_log()`(fsync + 写一行 `flush ok lines=... bytes=...`)
   ③ `game_exit_record()`(只能写一次:通道 + `exit.txt`)并通知 Java;
3. `GameActivity.onGameStopped()` -> `finishAndRemoveTask()` -> 300ms 后
   `Process.killProcess(Process.myPid())` —— **杀的是 :game 这一个进程**;
4. 主进程侧 `stop()` 起观察线程轮询 `/proc/<pid>`,确认 `:game` 消失(8s 窗口),
   日志写"确认 :game 进程已消失(主进程照常活着)"。

**没有**任何一步用"杀掉整个 App"实现结束游戏:`am force-stop` 只在验收脚本**每轮开始前**
清状态,不参与"结束游戏"这条路径。

## 6. 与核心库的收敛(2026-09-21)

核心库补齐了 `include/sxcl/jvm.h` + `src/services/launch/jvm.c`(`sxcl_jvm_build_env()` /
`sxcl_jvm_build_args()` / `sxcl_jvm_launch()`),**环境变量与 JVM 参数的拼法只许有这一份**,
所以本轮的 `android/app/sxcl_jre_bootstrap.c` 从"自己算 env + 自己拼 argv + 自己 dlopen"
收敛成**薄适配层**:

* 交给核心库:JAVA_HOME / LD_LIBRARY_PATH / TMPDIR / HOME / java.library.path 的计算、
  `-Djava.home`/`-cp`/`-Djava.library.path`/`-Dos.version` 的拼法、`<home>/lib` 与
  `<home>/lib/server` 的 RTLD_GLOBAL 预加载、`dlopen(libjli.so)` + `dlsym(JLI_Launch)` + 调用;
* 留在安卓侧(核心库不该管,而且是进程内起 JVM 特有的):**崩溃兜底**(pipe + 看门线程 +
  fatal 钩子 + `_exit(128+sig)`)、**日志出口钩子**(文件 + 通道 + logcat)、**JVM 收尾**
  (`DestroyJavaVM` 辅助线程,没有 JVM 时是空操作);
* 与 `android/jni/sxcl_jvm_bootstrap.c`(另一位同学的安卓薄封装)的关系:**两者定位不同**——
  那份只跑"起 JVM 打版本与属性"的自检(`sxcl_android_jvm_bootstrap` 不接受主类/classpath),
  本层要跑**游戏主类**(主类 / classpath / JVM 参数 / 游戏参数 / 收尾钩子),
  所以本层直接调核心库的 `sxcl_jvm_launch()`,不再自己算 env/argv,也不再自己 dlopen。
  **没有第二份 env/argv 实现**;唯一还留在两份文件里的是"把 LD_LIBRARY_PATH 交给 linker 私有入口"
  这一步(安卓特有),核心库选择的做法是 RTLD_GLOBAL 预加载 —— 本轮真机没有真 JRE,
  这一步同样走不到,接真包时以核心库那条为准(见 §8 待办)。

## 7. 边界为什么这样切(将来真要拆成两个应用时)

游戏运行器的边界已按**可搬家**的方式切开(§3):输入 jre / classpath / natives / 游戏目录 /
JVM 与游戏参数 / 渲染器;输出 日志流 / 退出码或信号 / PID / "结束游戏"命令;而且不依赖主进程的
UI 对象(GameHost.java 的 §A/§B 两段零 UI、零 Context)。将来若要拆成独立应用,只需把这一块
整体搬走(sxcl_game.c + sxcl_jre_bootstrap.c + GameActivity.java + §A/§B 的契约),再加上
显式 component 的 Intent 拉起与 Binder 上报即可,不需要重写运行器。**当前不开发独立应用版本**
(用户 2026-09-21:"先不开发 B,会莫名增大开发时间。")。
## 8. 还没做 / 下一步

1. **接游戏主类**(等 JRE 包):`--es gamejre <jre home>` 已经把 JRE 路径喂进运行器;
   缺的是"主类 + `-cp` + LWJGL/JNA 的 `-D`"(docs/18 §7.1)。`GameLaunchSpec` 已经把这几个字段备好。
2. **有 JVM 时的收尾**:`DestroyJavaVM` 那条分支本轮真机**没有 JRE,走不到**,只走通 flush 路径。
3. **LD_LIBRARY_PATH 的 linker 私有入口**:收敛后这一步归核心库(RTLD_GLOBAL 预加载);
   接真 JRE 包时要验一次"预加载够不够",不够就把 linker 入口补进核心库(只补一处)。
4. **渲染器**:spec 里的 `renderer` 只进边界与日志;把 `ANativeWindow` 递给未来的渲染层
   (LWJGL 的 Android 后端要它)是下一步。
5. **界面接线**:本轮由 boot 文件 / `am start --es action` 触发;产品化时接到启动页的
   "启动/结束游戏"按钮上(`GameHost.requestStart(spec)` / `GameHost.endGame()` 已经是对外接口)。
6. `docs/14-源码头注归档.md` 是自动生成的,本轮新增文件还没进那份归档。
