# 24 启动前的"补全文件"：PCL 在干什么，我们怎么补上

> 用户点名：「PCL 启动前会有一个"补全文件"的过程。看看他在干什么。然后给我个你的接下来计划」
> 本文 = PCL 精读（带行号）+ 三家对照 + 我们的现状 + 落地计划。
> 纪律：PCL/HMCL/FCL **只读**，未编译、未改动。

## 1 它在启动链的哪一步

`Plain Craft Launcher 2\Modules\Minecraft\ModLaunch.vb:113-124` 的启动主加载器是**定序**的：

| # | 阶段 | 权重 | 证据 |
| --- | --- | --- | --- |
| 1 | 获取 Java | 4 | `ModLaunch.vb:114` |
| 2 | 登录（McLoginLoader） | 15 | `:115` |
| 3 | **补全文件** `LoaderCombo("补全文件", DlClientFix(实例, False, True))` | **15** | `:116` |
| 4 | 获取启动参数 | 2 | `:117` |
| 5 | 解压文件（natives） | 2 | `:118` |
| 6 | 预启动处理 / 自定义命令 / 启动进程 / 等窗口 / 结束处理 | 1/1/2/1/1 | `:119-123` |

* `.Show = False` —— 它**不弹进度窗**，是"启动的一部分"。
* 第 3 个参数的语义：`DlClientFix(Instance, CheckAssetsHash, DownloadAssetIndexInBackground)`（`ModDownload.vb:54`）。
  启动这条路传的是 **`False, True`**：**启动时不校验 assets 的 hash**、**允许后台更新资源索引**。
* 同一条加载器还能单独跑：实例页的「补全文件」按钮（`PageInstanceOverall.xaml.vb:268-301`）传的是 **`True, False`**
  （强制校验 hash、强制重新下索引），并且**先检查"关闭文件校验"开关**——开着就提示
  「请先关闭 [版本设置 → 设置 → 高级启动选项 → 关闭文件校验]，然后再尝试补全文件！」（`:271-274`）。

## 2 补的是什么（两大块，逐块拆）

### 2.1 支持库（含**主 jar**）—— `ModDownload.vb:57-64`

```
"分析缺失支持库文件"  Task  ->  McLibNetFilesFromInstance(Instance)      (.ProgressWeight = 1)
"下载支持库文件"      Download(那份 NetFile 列表)                      (.ProgressWeight = 15)
→ LoaderCombo("下载支持库文件（主加载器）") { .Block = False, .Show = False, .ProgressWeight = 16 }
```

`McLibNetFilesFromInstance`（`ModMinecraft.vb:2062-2137`）按顺序凑出**四类**文件：

1. **主 jar**：`DlClientJarGet(Instance, True)`（`:2070`）。取不到**只记 warning**（"版本缺失主 jar 文件所必须的信息" `:2073`），
   不阻断——因为它已经进不了下载列表了，真正的问题是后面起不来。
2. **支持库**：`McLibNetFilesFromTokens(McLibListGet(Instance, False))`（`:2077`）。注意
   `McLibListGet`（`ModMinecraft.vb:1897-1945`）里做了两件关键事：
   * `McLibListGetWithJson(Instance.JsonObject)`（`:1901`，函数注释写着「**忽视继承**的支持库列表，即结果中没有继承项」）
     —— **继承链是在这里被解析/合并的**；
   * `IncludeMainJar=True` 时把**原版 client.jar 当成一条"库"**加进列表：`.LocalPath = <RealInstance>/<name>.jar`、
     `.Url = downloads.client.url`、`.SHA1 = downloads.client.sha1`（`:1941`）。
     它的"到底用哪个版本的原版"有一套兜底：HMCL 格式或没有 `jar` 字段 → 沿 `inheritsFrom` 一路找最深层
     （**但 1.17+ 的 Forge 不找**，`:1911-1917`）；找不到那个版本的 JSON → 只 warn「可能缺少前置版本」
     并退回自己（`:1928-1931`）。
3. **统一通行证 / Authlib-Injector**：按这个实例的登录方式（`VersionServerLogin` = 3/4）额外加两个 jar，
   带官方给的 hash（`:2080-2120`）。取不到下载信息时：本地已有就只 warn，没有才抛（`:2090-2096`）。
4. **"关闭文件校验"开关**：`ShouldIgnoreFileCheck`（`ModMinecraft.vb:2214-2216`）= 该实例的
   `VersionAdvanceAssets == 2` 或 `VersionAdvanceAssetsV2`。开着时把**已存在**的文件从列表里全剔掉
   （`:2122-2134`，「尽量忽略文件检查，这可能会保留有误的文件」——**存在就算过，不比对 hash**）。

每条 `McLibEntry` 转成 `NetFile` 时带一个 `FileChecker{ActualSize = Size（0 视为不检查）, Hash = SHA1}`
（`ModMinecraft.vb:2141-2151`）；**检查不在这一步做，而是交给多线程下载器**——
所以"分析"这一步很便宜（只构造清单），慢的活是下载器并行查。

> 顺带记两条它踩过的坑，值得抄：LabyMod 的文件**不校验**（`labymod` 特判，注释点 #3225，`:2148-2149`）；
> 四段坐标（`net.minecraftforge:forge:1.21.4-54.0.34:client`）目录名要**去掉最后一段**、文件名要保留（`McLibGet` `:2200-2208`，注释点 #7306/#5376）。

### 2.2 资源文件（assets）—— `ModDownload.vb:66-149`

```
"分析资源文件索引地址" (0.5) -> "下载资源文件索引" (2) -> "获取资源文件列表" (0.01, = McAssetsFixList) -> "下载资源文件" (25)
→ LoaderCombo("下载资源文件（主加载器）") { .Show = False, .ProgressWeight = 27 }
```

* 整个 `#Region` 被 `ShouldIgnoreFileCheck(Instance)` 一头挡掉（`:67-68`）：**开了"关闭文件校验"就连 assets 都不碰**。
* 索引地址：`DlClientAssetIndexGet(Instance)`（`:77`）——里面也是**沿 `inheritsFrom` 往上找 `assetIndex`**
  （`McAssetsGetIndex` `ModMinecraft.vb:2226-2239`）；找不到就 warn「未找到合适的资源索引下载地址，游戏 assets 可能缺失」（`:80`）。
* 启动这条路 `DownloadAssetIndexInBackground=True`：索引**只在校验不过时才下**（`:89-95`）；
  同时另起一个**后台**加载器更新索引，而且**一天只更新一次**（`:137-142`，比对本地索引文件的日期）。
  手动按钮那条 `False`：强制下到临时文件、下完 `Move` 覆盖（`:98-101, :112`）。
* `McAssetsFixList(Instance, CheckHash, ...)`（`ModMinecraft.vb:2347-2378`）两种模式，差别很大：
  * `CheckHash = True`（手动按钮）：只为每个资源对象构造 `NetFile`，**检查交给下载器**（`:2349-2355`）；
  * `CheckHash = False`（**启动这条路**）：当场自己查一遍，判据是**存在 + 大小**
    （`If File.Exists AndAlso (Token.Size = 0 OrElse Token.Size = File.Length) Then Continue For`，`:2369`）——
    **启动时不算 hash**，只补"没有的/大小不对的"；抛异常也只 warn（`:2373-2375`）。

## 3 一句话总结 PCL 的做法

> **"补全"= 把"这个版本运行需要哪些文件"翻译成一张带 (大小, SHA1) 的下载清单，然后交给多线程下载器：
> 缺失的下来、已存在且校验通过的一个字节都不下。启动前必跑一遍（权重 15、不弹窗），
> 手动按钮能再跑一遍（这次连 hash 一起校验）。支持库与主 jar 是一块，assets 是另一块。
> 有一个"关闭文件校验"的档位，开了就只补"完全不存在的"（assets even 直接跳过）。**

对照另外两家：
* **HMCL**：启动任务链里 `launch.state.dependencies` 这一阶段就是它（`HMCL\...\game\LauncherHelper.java:217,324-328`，
  阶段提示直接列了 `hmcl.install.assets` / `hmcl.install.libraries`），库的判断用
  `GameLibrariesTask.shouldDownloadLibrary(...)`（`:208`）。它**多一步**：`GameVerificationFixTask`（`:218`）
  会**改 jar**——pre-1.6 的 Forge 版本删掉 `META-INF/MOJANG_C.DSA` / `.SF`（那个任务的全部内容，74 行）。
* **FCL**：同一个 HMCL core（`GameAssetDownloadTask` / `GameLibrariesTask` 在它的 `DefaultDependencyManager` 与启动流程里）。

## 4 我们现在是什么样

* 启动层**不做补全**：`src/services/launch/driver.c:573` 的注释就是「**缺什么原样带出去（不做补全，只报告）**」，
  `out->missing` 拷的是 `out->log.missing`。
* 「缺什么」是**从游戏自己的日志里读出来的**（启动结束后扫 stdout/latest.log，见 `docs/17`/`docs/20`）——
  也就是**游戏已经崩了才知道**。用户看到的是"缺少 XXX.jar"，还得自己去重装。
* 我们**已经有全部零件**，而且比 PCL 那套强：
  * `include/sxcl/manifest.h:48 sxcl_version_plan_build()`：从版本 JSON 直接生成"该下哪些库/资源"的计划
    （安装流程一直在用）；
  * `include/sxcl/engine.h`：多线程下载 + **每条候选路重试** + `max_conn_per_file` 分片 + `rate_bps` 限速 +
    `sxcl_task_verify_state`（`VERIFY_HASH`/**`NONE` 不许当"已存在"`**）+ **`skipped_existing` 结构化统计** +
    **hashcache（`cache_path`）**——注释里写着这一条就是为"第二次运行要核对 5000+ 个资源文件"准备的。
* 也就是说：**PCL 的"分析 + 下载器自己查"这套，我们的引擎天生就是这么设计的**，缺的只是"在启动前把它们串起来"。

## 5 计划

### P0（立刻做）：启动前补全文件 —— 12-20h

分两刀落地，第一刀就能止血：

**P0a · 支持库 + 主 jar（6-10h）**
1. 核心：新入口 `sxcl_launch_complete(...)`（放 `src/services/launch/` 或复用 `manifest.c` 的计划器）：
   * 输入：合并后的版本 JSON（我们刚做的拍平/兜底正好保证它是完整的）+ 游戏目录 + 实例名；
   * 用 `sxcl_version_plan_build` 生成计划 → **补两条 PCL 有、我们的计划器现在可能没有的东西**：
     主 jar 那条 (`downloads.client` → `versions/<实例>/<实例>.jar`)、以及 `jar` 字段/继承兜底；
   * 交给引擎跑；靠 `skipped_existing`/`verify_state` 保证"齐了一个字节都不下"。
2. 接线：`driver.c` 在**第 4 步（拼参数）之前、natives 之前**插一段（顺序按 PCL：补全 → 拼参数 → 解压 natives）；
   开关 `launch.complete_files`（默认开）+ 一个 `launch.skip_file_check`（等价 PCL 的"关闭文件校验"：
   只补完全不存在的）；进度走现成的 `on_progress`。
3. 失败口径：补不下来的文件不进"致命"——按 PCL 的做法**只 warn 并继续**，但在结论里如实写"缺 N 个文件"
   （我们现在已经会报，只是现在只能从日志里读到）。

**P0b · assets（6-10h）**
4. 资源索引：沿继承找 `assetIndex`（我们拍平后它就在实例 JSON 里了）+ 索引缺失/损坏 → 重下；
5. 资源对象：**启动时只查"存在 + 大小"**（照 PCL `:2369`），hash 交给下载器在必要时做（`VERIFY_HASH` + hashcache）；
   手动"补全文件"入口用 `VERIFY_HASH`（照 PCL 的 `CheckHash=True`）；
6. 后台索引更新（每天一次）—— **先不做**，等 P0 稳了再说。

**验收（必须能证明"齐了不下"）**：
* 夹具四种：全齐 / 缺一个库 / 大小不对 / 缺主 jar → 断言"缺的补上、齐的 `skipped_existing == 1`、字节数 0"；
* 真机：拿 `docs/23` 里那个 `1.21.11-flat3`，**删掉一个库**再启动 → 自动补回来；
* **反向夹具**：把 `versions/1.21.11-flat3/1.21.11-flat3.jar` 删掉 → 必须自己下回来（31 MB，走镜像候选）；
* 假--dry-run 不能装样子：`--dry-run` 也必须真的补（PCL 就是这样，补全在"拼参数"之前）。

### 6.1 同一轮里挖出并修掉的启动 bug：`${arch}` 占位符

**症状**（用户在这台机器上真启动时撞到的）：启动 PCL 装的 `1.8.9-Forge_11.15.1.1902-OptiFine_M5` 直接失败——
`准备原生库失败:版本 JSON 里库 tv.twitch:twitch-platform:6.5 的 natives 分类器 natives-windows-${arch} 没有下载路径`。

**原因**：1.8.x/1.9.x 的版本 JSON 里 `natives.windows` 写的是 **`natives-windows-${arch}`**，
而 `downloads.classifiers` 里的键是 `natives-windows-64` / `-32`。我们的两处查表都按**原样**查：
`src/services/minecraft/natives.c`（解压原生库）与 `src/services/metadata/manifest.c`（把原生库 jar 加进下载计划）——
于是老版本的原生库既进不了计划、也解不出来，**整个启动被拦下**。

**修法**：新增 `sxcl_natives_classifier_of()`（`natives.h`/`natives.c`），一处逻辑两处共用：
① 原样能找到就用原样的；② 键里有 `${arch}` 时按 **64 → 32** 展开再找；
③ 都没有则返回 NULL 并把**原始键**回填（报错里必须看得见原样，不能只看到展开后的）。

**验收**：`sxcl_natives_test` 新增 13 项断言（64 优先 / 只有 32 时退 32 / 无占位符时不动 / 都没有时 NULL + 原始键），
该测试 49 项全过；**真机**：同一个 1.8.9 实例 dry-run 从"启动被拦下"变成
`natives: 解出 14 个文件` + `结论: 只准备不启动:Java 与参数都已就绪`，
补全清单也从 35 件涨到 37 件（那两个 `-64` 分类器现在真的进了计划）。

## 6 P0a 已落地（2026-09-22）

**做了什么**：启动层在"选 Java"之后、"写 options.txt / 解压 natives / 拼参数"之前插了一步"补全文件"（PCL 的第 3 步）。核心是新的 `sxcl_version_plan_fetch()`（`manifest.h`）：把 `sxcl_version_plan_build()` 算出来的清单（依赖库 + 客户端 jar + 资源索引）交给**现成的下载引擎**跑一遍 —— 镜像候选 / 多路重试 / 分片 / 限速 / 断点续传 / 哈希缓存，全都是安装流程用了很久的那一套。

**口径**（与 PCL 逐条对齐）：

* **dry-run 也补**：补全在"拼参数"之前，不补的话自检出来的命令行指着一堆不存在的路径；
* **补不齐不拦启动**：失败只如实记进结果（`complete.files_failed` / `complete.error`）+ 日志一行，与 PCL 的"只 warn 不阻断"一致；`missing`（从**游戏日志**里读出来的那份）保持不变；
* **齐了一个字节都不下**：靠引擎的"已存在且校验通过"快路径，统计看 `skipped`；
* 开关：`req.complete_files` + `req.engine_opts`（没有传输后端就自动退化成"只报告"）；
* 镜像优先：`req.prefer_mirror` 与安装同口径（`download.source` = bmclapi/auto 时置位）。

**接线**：界面 `launch_worker.cpp` 建一份 `CompleteOpts`（设置文件里的 workers/限速/分片/哈希缓存 + Qt 传输后端），**准备那一遍**带着它跑；**真正起进程那一遍不再补**（`complete_files = 0`）—— 同一秒再核对几千个文件纯属白烧 IO。命令行 `sxcl-dl launch` 同样接上了（`--verbose` 时逐文件打印）。

**验收**：

| 项 | 证据 |
| --- | --- |
| 单测 | `sxcl_launch_driver_test` 的 `case_g_complete()`：**假传输后端**在内存里当 HTTP —— 文件都在时断言 **0 次请求**；删两件后恰好下载 2 件（128 字节）、第三件命中已有；404 时不拦启动；取消时如实记"已取消"；没有 `engine_opts` / 关掉开关都不补。该测试 81 项断言全过 |
| 两棵树全套 | 核心 46/46、界面 49/49 |
| 真机（真网络） | 合成夹具（两个真实小库 + 客户端 jar）：第一次"共 3 件，命中已有 0，下载 3（85938 字节）"；第二次"**命中已有 3 件，下载 0 件，写了 0 字节**" |

**踩到的两个坑**（都写进代码注释了）：

1. 引擎把 `opts->userdata` 传给 `transport_factory`，而补全为了进度桥必须换掉 userdata → 传输后端拿到的是错指针（假后端直接崩在写内存）。修法：`manifest.c` 里**转发**工厂，把调用方自己那份 userdata 还给它（同一模式在 `install.c` 的 `default_download` 里也在用，只是那里的 Qt 工厂恰好忽略参数，所以一直没暴露）。
2. 测试夹具的 `write_text` 是**位置写、不截断**：内容变短时旧尾巴留在文件里，JSON 就成了"合法值 + 多余内容"（解析报"根值之后还有多余内容"）。修法：先删再写。这是夹具层的坑，与产品代码无关，但它差点把这一轮的所有用例一起打红。

**还没做**：

* "关闭文件校验"档位（PCL 的 `ShouldIgnoreFileCheck`）：只补**完全不存在**的、存在的不比对 —— 设置键先留着，下一轮做；
* ~~**assets 对象（P0b）**：本轮清单里只有资源**索引**~~ → **已在 §7 落地**；
* 补全过程中的**进度条/取消按钮**：核心库接口已经支持（`complete_is_cancelled` + 转发 `on_progress`），界面还没显示，也没接取消按钮；

## 7 P0b 已落地（2026-09-22）：资源对象也一起补

**上一轮缺口**：清单一度只有 `assets/indexes/<id>.json`（几百 KB），**没有**它里面列的 5000+ 个对象（`assets/objects/ab/abcdef…`）。
PCL 这条路是**两遍**跑的（`ModDownload.vb:70-104`）：第一遍下依赖库 + 主 jar + 资源索引，第二遍**读索引把对象展开**再下一遍。这一轮补上第二遍。

**实现**：`sxcl_version_plan_add_asset_objects()`（`manifest.h`/`manifest.c`）此前只在下**安装器**里被调用；
这轮加了 `_ex` 变体（多一个 `verify_hash`），**老入口 = 强校验的薄包装**，安装器行为一字不改。
启动前补全在 pass1（库 + jar + 索引）完成后，读 game 目录里那份索引、把每个对象的 `hash`/`size` 加进任务表，
用**同一份** `engine_opts` 再跑一遍；两遍的统计合并成一份（见下）。

**三档 `launch.complete_assets`**（`sxcl_launch_request.complete_assets`）：

| 值 | 含义 | 场景 |
| --- | --- | --- |
| 0 | 不补资源（只有库 / jar / 索引） | 快速启动、离线反复重启 |
| **1** | **默认**：补对象，按索引里的 `size` 判"在不在" | 与 PCL 启动口径一致（`DlClientFix(…, CheckAssetsHash := False, …)`）|
| 2 | 强校验：每个对象按索引里的 `sha1` 对 | 怀疑资源被改坏 / 手动「补全文件」 |

**统计口径**（两遍合并时的坑，已修）：`total`/`skipped`/`failed` 取**第二遍**的值（第二遍的清单才是"该有的全集"），
`downloaded`/`bytes_done` **两遍相加**。一开始三样都相加，导致同一件库在第二遍又失败一次、报"失败 2 件"。

**第二遍为什么不能偷懒**：pass2 不能再调 `prefer_mirror`（那会打乱用户显式选的源），
所以 `complete_assets_pass()` 自己按 `req.prefer_mirror` 排了一次镜像顺序。
