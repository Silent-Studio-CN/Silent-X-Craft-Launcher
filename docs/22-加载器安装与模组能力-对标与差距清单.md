## 1 第一问：MOD 列表是怎么拉的

### 1.1 对照

| 维度 | PCL | HMCL |
| --- | --- | --- |
| 数据源 | **双源**：CurseForge + Modrinth 各拉一页再合并（`Modules/Resource/ResourceSearcher.vb:73` CF、`:99` Modrinth） | **一主一辅**：Modrinth 当主库（`addon/repository/ModrinthRemoteAddonRepository.java:112`），CF 另有实现（`CurseForgeRemoteAddonRepository.java:56`） |
| 服务端筛选 | `facets=[…]`（`ResourceSearcher.vb:110`；写法示例就在 `:102` 的注释里） | `List<List<String>> facets`：`project_type:` / `versions:` / `categories:`（`ModrinthRemoteAddonRepository.java:169-179`） |
| 分页 | CF 用 `index=`（offset，`ResourceSearcher.vb:90`）；Modrinth 用 offset/limit | `NetworkUtils.withQuery(PREFIX + "/v2/search", …)`（`:185`） |
| 排序 | CF `sortField=2`（下载量）+ Modrinth `index=relevance` | Modrinth 原生 index |
| 详情 / 版本列表 | 同一功能两套：`ResourceProject.vb:396`（CF）/`:398`（Modrinth）；版本 `ResourceVersion.vb:235`（CF files）/`:256`（Modrinth version） | `ModrinthRemoteAddonRepository.java:405-500` |
| API Key | CurseForge 要 `x-api-key`，**按 URL 主机**注入（`Modules/ModSecret.vb:36`） | 同样按主机注入（`util/io/NetworkUtils.java:174`） |
| **镜像** | **字符串换主机**：`api.modrinth.com → mod.mcimirror.top/modrinth`、`api.curseforge.com → mod.mcimirror.top/curseforge`（`Modules/Minecraft/ModDownload.vb:1309-1312`） | **候选注入**：同样的两条映射放进 `BMCLAPIDownloadProvider.java:102,104`，由 `injectURLWithCandidates` 让同一个请求自带第二条路（`ModrinthRemoteAddonRepository.java:185`） |

**一句话**：两边都是「服务端 facet 筛选 + 客户端兜底」，都**给社区资源 API 也配了镜像**（`mod.mcimirror.top`）。我们仓库**连一个模组源都没有**（见 §3 A1）。

### 1.2 「优先匹配已有版本」= 置顶推荐，不是过滤

* PCL：工程详情页给卡片排序的 `CardSorter` 里有一档明确写着 `'置顶`
  （`Pages/PageDownload/Resource/PageDownloadCompDetail.xaml.vb:51-57`，排序链 `:67-101`，末尾 `:101` 用 `Distinct`）。
  **本地已有的版本被排到最前，其余版本照常列出、照常可点** —— 不是「只显示匹配的」。
* HMCL：对应逻辑在**本地文件侧**——`addon/mod/LocalModFile.java:204-205` 按 `gameVersions()` 与 `loaders()` 过滤出
  「这个本地文件能用的版本」，用在**更新检查**里，同样不影响浏览列表。
* 更新检查：PCL 走 Modrinth `/v2/version_files/update_individual`（`LocalResourceLoaders.vb:180`），
  **按发布日期**比大小（不用 semver）。

### 1.3 依赖：只展示，不自动装

* PCL：`PageDownloadCompDetail.xaml.vb:520` 把依赖列表 `Deps.Sort()` 出来给用户看。
* HMCL：依赖是一等公民（`addon/RemoteAddon.java:215,225`、`ModrinthRemoteAddonRepository.java:405-410`），
  但用在**装整合包**时的解析；浏览单个模组只列。
* 两边**都不自动换加载器**：版本与当前实例的加载器不匹配时**静默跳过**该文件，不会反问「要不要顺手装个 Forge」。

### 1.4 同名冲突：学 HMCL，不学 PCL

* PCL：**静默覆盖**（同名文件直接写下去）。
* HMCL：**拦下并改名**（`ui/instances/ModListPage.java:217-244` 的 `LocalModFile[]`，`:290` 的 `rollback(from,to)`
  说明旧文件被留着而不是删掉）。
* **本仓采用 HMCL 口径**：同名先拦、给「改名 / 保留旧文件」的选择。

## 2 第二问：模组加载器有哪几种装法

| 加载器 | HMCL | PCL | 本质 |
| --- | --- | --- | --- |
| Fabric / Quilt | 进程内 patch：只下 profile json 拼进版本 JSON，**不跑安装器**（`download/fabric/FabricVersionList.java:49-55`、`download/quilt/QuiltVersionList.java:49-55`，实现 `QuiltInstallTask.java:53,84-137`） | 支持 Fabric，**没有 Quilt** | 纯元数据 |
| Forge ≤ 1.12（legacy） | jar 里有 `install`+`versionInfo` → 直接解包（`ForgeOldInstallTask.java:93`） | 外判注入器 | 解包 |
| Forge 1.13+ / NeoForge | **installer.jar 只当数据容器 + 进程内重建 + 跑 processors**：`ForgeNewInstallTask.java:124-153`（起 Java）、`:155-185`（每个 output SHA-1）、`:77-110`（全命中即跳过 = 幂等）、`:305-324`（从 jar 拷 maven）、`:356-384`（DOWNLOAD_MOJMAPS 特判） | 外判内置的 `com.bangbang93.ForgeInstaller`（`PCL/ModDownloadLib.vb:948,950`），但**跑之前自己先分析并下好支撑库**（`:1153-1197`） | 重放 processors |
| 新旧分流依据 | **内容判定**：含 `spec` → 新；含 `install`+`versionInfo` → 老；都不是 → 抛异常（`ForgeInstallTask.java:137-155`，本地 jar 同套 `:176-201`） | **版本号启发式**：loader 主版本 ≥ 20 → 注入器（`ModDownloadLib.vb:1150`） | — |
| 成功判据 | 每个 output 的 SHA-1 + 异常 | 只看**末 5 行**有没有 `true`（`ModDownloadLib.vb:1027`），**不看退出码** | — |

**推荐模型（不变）**：HMCL 式 —— *installer.jar 只当数据容器 + 进程内重建 + 只在 profile 声明 `processors` 时逐个执行 + 对声明的 output 做 SHA-1（不匹配即失败，全命中即跳过）*。

| 事项 | FCL 怎么做 | 对我们的意义 |
| --- | --- | --- |
| 写盘形态 | **拍平**：`MaintainTask.maintainPreservingPatches`(`fclcore/download/MaintainTask.java:106-111`)= 先 `resolve()`（`Version.java:292` 把 `inheritsFrom` 写死 null）再 `setPatches(...)`；落盘 `VersionJsonSaveTask.java:50-54` → `versions/<id>/<id>.json`。**读盘仍兼容继承式**（`resolve`/`resolvePreservingPatches`） | **正是用户点名要学的形态**：写盘自包含、读盘兼容 —— 我们的实现走同一条（见 `docs/23`） |

| 已安装识别 | `ModDependenciesResolver.java`（**FCL 自研**，无 HMCL 头）：文件名 + `hash → /v2/version_file` 反查项目 id；本体已装跳过、**前置仍装**；只自动装 REQUIRED、BFS 上限 50 | 比 PCL 的"置顶推荐"更进一步；我们做模组时照它 |
| 同名 mod | 下载与导入两条链路都是 **REPLACE_EXISTING 直接覆盖**（`DownloadPage.java:948-950`、`FileDownloadTask.java:227-235`、`ModManager.java:265-271`），无备份/改名/提示 | 与 PCL 一致（HMCL 的"拦下改名"是它 UI 层独有的） |
| 加载器源 | 进程内 patch（Fabric/Quilt/Forge 都是），**不跑安装器** | 我们 方式 A 跑安装器是自研路线（见 `docs/23` §3 的坑） |

## 4 本轮把两个悬案钉死了（含工期修正）

### 4.1 `xz.c` **不支持** `.lzma`（alone 格式）—— 但**根本不需要**（FCL 已证）

> **2026-09-22 更正**：FCL 精读（§7）证明 **HMCL/FCL 跑 Forge processors 时压根不解 `data/*.lzma`** ——
> 它们只是把安装器 zip 里那个文件**原样复制**到临时目录（`ForgeNewInstallTask.java:415-427`），
> 然后把路径交给 processor 自己处理（`[...]`/`{VAR}`/`'literal'` 三种字面量在 `:242-299` 解析）。
> 所以 **A3 完整重放的工期回到 12-20h，不含任何 LZMA 工作**。下面是当时的核实过程，保留备查。

* 结论是**明确写着的**：`include/sxcl/xz.h:36`「不解 `.lzma`(alone 格式)与 `.lz`(旧 lzip)」；
  支持的过滤器只有 LZMA2（`xz.h:27-28`）。
* 但 **LZMA1 解码内核已经在里面**、而且与 LZMA2 的外壳是分开的：
  `lzma_set_props`（`xz.c:503`，属性字节 < 225 的 lc/lp/pb 解析）、`lzma_reset_state`（`:481`）、
  `lzma_literal`（`:547`）、`lzma_symbol`（`:591`）、窗口管理 `win_*`（`:263-376`）。
  LZMA2 那条路（`lzma2_decode_chunk` `:673`、`lzma2_run` `:703`）只是给同一个内核套了分块 + 状态重置的壳。
* **所以「支持 `data/*.lzma`」= 解析 13 字节 alone 头（属性 + 字典大小 + 未压缩大小）+ 直接驱动 `lzma_symbol` 到约定长度**，
  不需要新写解码器。工期从「+4-8h」修正为 **+2-4h**（含一个真实 Forge `data/*.lzma` 夹具与一处 CRC/长度自检）。

## 8 A3 已落地（2026-09-22）：processors 重放

**为什么它是最要紧的一条**：1.13 以后的 Forge **安装器不再自己装东西**。真正的活是
`install_profile.json` 里那串 processor 干的 —— installertools 拆 MCP 映射、jarsplitter 把原版 jar
拆成 slim + extra、ForgeAutoRenamingTool 按 SRG 重命名、binarypatcher 打二进制补丁。
以前方式 B（解包安装）只做五件事就报"安装成功"，装出来的实例**要么没有客户端主 jar、
要么是没打过补丁的原版**。

**参考实现**：FCL `fclcore/download/forge/ForgeNewInstallTask.java`（ProcessorTask /
parseLiteral / patchDownloadMojangMappingsTask）与 `ForgeNewInstallProfile.java`
（`Datum` / `Processor.isSide`）。逐条对齐，两处**故意不同**写在表里。

| 环节 | FCL | 我们 |
| --- | --- | --- |
| 跑哪几条 | `sides == null \|\| sides.contains("client")` | 同款；**没有 sides 键 = 两侧都跑**，空的 sides 数组 = 都不跑 |
| data 取值 | `Map<String,Datum>`，只取 `client` | 同款，兼容"直接是字符串"的老格式 |
| 值求值 | `parseLiteral`：`[坐标]` / `'字面量'` / `{键}` / 其余当"安装器 zip 里的文件"取到临时目录 | 同款（`sxcl_processor_eval`）；**zip 里没有前导斜杠**，所以查条目之前先去斜杠（FCL 走 zip 文件系统，能直接开绝对路径）—— 这一条是真机前差点漏掉的 |
| 产物幂等 | 先看 outputs：全在且 SHA-1 对 → 跳过（**此时不要求工具 jar 在磁盘上**） | 同款，顺序一模一样（重装前清过 libraries/ 也不会因此失败） |
| 命令行 | `java -cp <classpath…>;<jar> <Main-Class> <args…>`，Main-Class 读 jar 的 MANIFEST.MF | 同款；分隔符 Windows `;` / 其它 `:` |
| 失败重试 | Java 8 → 17 → 11 → 21 | 换**路径**：调用方给的 java → `%JAVA_HOME%/bin/java` → PATH 里的 `java`（"按版本号挑 JRE"那套元数据还没接上来） |
| 跑后校验 | 每个 output 存在 + SHA-1 对，否则删掉再抛 | 同款；错误里带上"期望 / 实际" |
| MOJMAPS | `patchDownloadMojangMappingsTask`：改从版本 JSON 的 `downloads.client_mappings` 下（官方站点在国内常连不上） | 接口留好了（`ctx.download_mappings`）：**调用方没接就照常跑处理器**（官方网络能通照样装完），界面接线排在下一步 |
| LZMA | 不解 `data/*.lzma`，只把文件取出来交给处理器 | 同款 |
| `MINECRAFT_VERSION` | FCL 误写成了 jar 路径 | 给**版本号**（实测 1.20.1 的处理器根本不看它） |

**落点**：

- `include/sxcl/processor.h` + `src/services/modloader/processors.c`：访问器 / 求值 / 幂等 /
  命令拼装 / Java 重试 / 跑后校验；**起进程走 `ctx.run` 回调**，于是日志、超时、取消
  全都是安装流程那一套（同一个 process.h）；
- `installer.c`：方式 B 的顺序变成 **解包 maven/ 与通用 jar → `on_libraries` 下依赖库 →
  重放 processors → 复制原版 jar → 写版本 JSON**（写 JSON 仍是最后一步，"有 JSON"才等于"装完了"）；
  处理器失败 = 这次安装失败，绝不留一份"看着装好、其实没打补丁"的实例；
- `loader.h`：`sxcl_loader_library` 多一个 `url_full`（清单里给的 `downloads.artifact.url`）；
  `collect_libraries` 现在收三处（`libraries[]`、`processors[].classpath[]`、`processors[].jar`），
  并且**优先用清单给的绝对地址** —— 实测 Forge 1.20.1 那 46 条依赖里 jsr305 在
  libraries.minecraft.net、其余在 maven.minecraftforge.net，只按 maven 根地址拼会 404；
- `install.c`：方式 B 的库下载排三条候选（清单给的绝对地址 → 它的镜像
  `sxcl_manifest_mirror_url` → maven 根地址 + 路径），`prefer_mirror` 时镜像排第一，
  与安装器 / 资源对象同一个口径；
- `sxcl-dl loader` 补上 `on_libraries`（以前**没接**，方式 B 等于下不了库）与
  `--extract-install`（跳过安装器 CLI 直接走方式 B —— 既是排查兜底，也是这条路自己的
  端到端验收入口）；新开关 `force_extract_install` 落在 `loader.h`，GUI 暂不暴露。

**验收**：`tests/processor_test.c`（新增，**84 项断言**）：自带一个"只写 stored 条目的最小 ZIP
写入器"造真 jar 夹具（仓库里不放二进制夹具），假 run 回调记录命令行 —— 覆盖 side 过滤 /
求值（`[坐标]`、`'字面量'`、内联 `{键}`、缺键与括号不闭合要报错）/ outputs 幂等
（产物齐了、工具不在也跳过）/ 产物哈希不符要报错并删件 / classpath 与 Main-Class 拼装 /
Java 候选重试 / 取消返回 2 / dry-run 不跑 / data 裸值取文件（含"没给 take_file 就如实报错"）。

## 9 A2 已落地（2026-09-22 晚）：版本隔离

**概念基础**（docs/23）：版本 = `versions/` 下的文件夹名。隔离就是让**这一个版本的数据目录变成它自己的文件夹**：

| 路径 | 隔离关（默认） | 隔离开 |
| --- | --- | --- |
| `--gameDir`（游戏读写数据的地方） | `<根>` | `<根>/versions/<版本名>` |
| `--assetsDir` | `<根>/assets` | **仍是** `<根>/assets` |
| classpath（`-cp`） | `<根>/libraries` | **仍是** `<根>/libraries` |
| `options.txt`（渲染后端写这儿） | `<根>/options.txt` | `<根>/versions/<版本名>/options.txt` |
| natives | `versions/<版本名>/<版本名>-natives` | 不变（解压逻辑没动） |

开了以后第一次启动会在隔离目录里建好这一串（已存在不动、不复制、不删任何东西）：
`mods` / `saves` / `config` / `resourcepacks` / `shaderpacks` / `logs` /
`crash-reports` / `screenshots` / `server-resource-packs`。

**落点**：

* `include/sxcl/isolation.h` + `src/services/launch/isolation.c`：目录计算、子目录清单、建目录
  （`sxcl_launch_isolated_dir` / `sxcl_launch_isolated_subdirs` / `sxcl_launch_prepare_isolated`）；
* `driver.c`：读 `general.version_isolation`（默认关）→ 备好隔离目录 → 把 `--gameDir` 换成它，
  **显式**把 `assets_root` / `library_directory` / `client_jar` 指回根目录与
  `versions/<版本名>/<版本名>.jar`（不显式给的话 `args.c` 会按 `--gameDir` 相对拼出
  `versions/<版本名>/assets` 这种不存在的路径）；
* 结果里多两个字段 `isolated` / `isolated_dir`，并且 `game_dir` 报**实际生效**的那个；
* 设置页那张卡片（以前是死开关）文案改成"每个版本各用一套 mods / saves / config / options.txt
  （assets 与 libraries 仍然共用；默认关）"。

**验收**：`tests/launch_driver_test.c` 新增 `case_h_isolation`（该用例 **107 项断言全过**）：
隔离开时 `--gameDir` 指 `versions/1.21.4`、classpath 仍含 `libraries`、`options.txt` 写进隔离目录、
`mods/saves/config` 真建出来；关掉后 `--gameDir` 与 `options.txt` 回到根目录（老用户升级上来行为不变）。

**下一步（P3 / A1 模组页）**：隔离到位以后模组页才谈得上"装进 `versions/<实例>/mods`"
—— 否则所有版本共用一个 `mods/`，装了就是互相打架。

  下一轮网络可达时补跑：`sxcl-dl loader quilt <loader> 1.20.1 <夹具> --installer <quilt-installer.jar>`。

### 10.2 顺带挖出来并修掉的引擎 bug：半截传输被当成"下完了"

**怎么撞出来的**：下 Quilt 安装器（8.3 MB）时，源站把连接掐在半路，结果呢 ——
引擎报 **"成功"**，磁盘上是一个 **8,734,533 字节**的文件（大小**正好等于**期望值），
可后面 6 MB 全是 0，一直到 `java -jar` 报 `Invalid or corrupt jarfile` 才暴露。

**根因**：单连接下载会把 `.part` **预分配到最终大小**（为了断点续传），于是"文件大小 == 期望大小"
**永远成立**；任务只有 `size` 没有 `sha1` 时（安装器/加载器依赖库就是这种），
收尾的 `sxcl_verify_file_cached(part, size, NULL, …)` 只比大小 —— 半截文件照样通过、改名、报成功。

**修法**（`src/core/dl/engine.c`，两处）：

* 单连接：读到 EOF 后先看**实际写下多少字节**（`offset`）——
  `finished && size > 0 && offset < size` 就按"传输提前结束"记一次源失败、回到重试/换路续传；
* 分片：同样看 `"各分片游标之和"` 与 `size` 的差，不够就把 `ok` 打掉、如实报
  `"分片传输提前结束(只到 x/y 字节)"`。

修完当场复测：同一个 URL 现在**如实失败**，并且**不留下任何文件**（以前会留下一个 8.3 MB 的假货）。

**回归用例**：`tests/launch_driver_test.c` 的 `case_g_complete` 新增 `g9` ——
假传输后端"声明 64 字节却只给 16 字节"，断言三件事：不拦启动、**如实记失败**、半截内容
**绝不落到正式路径上**（该用例 110 项全过）。

## 11 B4 结构预判分流（2026-09-22 晚）

**以前**：方式 A 对 Forge/NeoForge **无条件按 4 组命令行依次试**，每组默认 30 分钟超时
（`loader.h` 的 `SXCL_LOADER_DEFAULT_TIMEOUT_MS`）—— 撞上一个装不了的安装器，用户要等**两小时**
才看到失败；而且全文没读过 `install_profile.json` 的 `spec`。

**现在**（`loader.h` + `compat.c` + `installer.c`）：

* `sxcl_loader_installer_format_of(profile_json, len)`（**纯函数**，可单测）判形态：
  * **1.13+ 新格式**：`spec >= 1` / 有 `processors` / 有 `json`（指向 jar 里的 version.json）任一成立；
  * **1.12- 老格式**：有 `install` 或内嵌 `versionInfo`；都不是 = **UNKNOWN**；
* `sxcl_loader_installer_probe(jar)`：真去开 jar 读 `install_profile.json`（读不到 = UNKNOWN）；
* `run_installer_phase()` 按形态分流：
  * UNKNOWN → **当场如实失败**（"这不是一个能静默安装的加载器安装器"）并且**不回退方式 B**
    （方式 B 同样要这份 profile），省掉两小时；
  * 新格式 → 只留 `--installClient` 那几组（`--installDir=` 是 1.12- 的旗标，在新安装器上纯属浪费一轮）；
  * 老格式 → 照旧全试，但**总预算按组数摊开**（每组至少 60 秒）；
  * 三种情况都报一句人话（命令行/界面日志里看得见"这次打算怎么装"）。

**真机验收**（夹具 = 1.20.1 原版 + 真 Forge 47.2.0 安装器 + 一个"秒退"的假 java）：

| 场景 | 结果 |
| --- | --- |
| 真 Forge 1.20.1 安装器 | `安装器形态：1.13+ 新格式(spec/processors) → 先试 3 组命令行（每组最多 600 秒）`，随后只有 `现代 --installClient <目录>` / `现代 --installClient（装到当前目录）` / `兜底 --installClient --target` —— **旧 --installDir= 那一组被滤掉了** |
| 随便一个 jar（不是安装器） | `安装器里没有 install_profile.json —— 直接判失败（不再盲试命令行）` + `回退方式B=否`，**0 秒失败** |

**单测**：`tests/loader_test.c` 新增 `test_installer_format`（11 项）：新格式三条判据
（spec / processors / json）各自成立、老格式的 install+versionInfo、空文本/非 JSON/只有 libraries
三种"认不出来"、形态名、probe 对不存在与不是 zip 的文件都返回 UNKNOWN。该测试 **328 项全过**。

## 12 A4 安装器哈希 + 镜像三前缀（2026-09-22 晚）

**A4-① 安装器也带官方哈希**（`install.c` 的 `stage_loader_installer`）：

* 下载安装器**之前**先取 `<安装器 URL>.sha1` —— 各家 maven 都发布这个侧车；
* 侧车本身也走同一条候选路（`prefer_mirror` 时先问镜像，再问官方），拿不到**不是错误**，
  如实退回老口径（"只校验下下来了且非空"）;
* 拿到 40 位十六进制就 `task.sha1 = …` —— 于是：**强校验**（半截/被换过的安装器不会再被接受）
  + 白拿"已存在且校验通过 -> 一个字节都不下"的快路径（重装同版本时省一次几 MB 下载）;
* 日志里会写一句 `加载器安装器带官方 SHA-1 校验: …`，排查时看得见。

**A4-② 三个加载器 maven 的镜像**（`manifest.c` 的 `sxcl_manifest_mirror_url`）：

以前映射表只有 5 个主机（launchermeta / piston-meta / piston-data / libraries.minecraft.net /
resources.download.minecraft.net）—— **三家加载器的 maven 一条镜像都没有**：GUI 里"安装器自己下
几百 MB"那一段完全绕开镜像，静默退化成官方单路。现在补上（都走 BMCLAPI 的 `/maven/` 前缀）：

| 官方前缀 | 镜像 |
| --- | --- |
| `https://maven.minecraftforge.net` | `https://bmclapi2.bangbang93.com/maven` |
| `https://maven.neoforged.net/releases` | 同上 |
| `https://maven.fabricmc.net` | 同上 |
| `https://maven.quiltmc.org/repository/release` | **不映射**（BMCLAPI 对它 404，映射只会多一条必死的候选） |

**实测（2026-09-22 晚逐个 HEAD）**：Forge 安装器 5,973,950 字节 / fabric-loader 1,327,691 /
neoforge 安装器 6,798,614 / Maven Central 的 gson 240,400 —— **全是 200**。

**单测**：`tests/manifest_test.c` 新增 5 条映射断言（Forge/Fabric/NeoForge 各一条 + Quilt
必须返回 -1），该测试 **80 项全过**；`tests/install_test.c` 的假 IO 不给 `.sha1` →
侧车取不到就退老口径，**274 项照旧全过**（证的正是"拿不到不是错误"）。

## 14 A1 第二个源：CurseForge 的结构与「没配 key 就不查」（2026-09-22 晚）

PCL 是**双源**（CurseForge + Modrinth）。CF 与 Modrinth 有两处根本不同，决定了这一层的形状：

1. **必须带 `x-api-key` 头**（用户自己去 console.curseforge.com 申请）——

**落点**（`sxcl/mods.h` + `src/services/mods/mods.c`，与 Modrinth 那一半同一个文件、同一套结构）：

| 函数 | 作用 |

| `sxcl_mods_curseforge_class_id(type)` | mod=6 / shader=6552 / resourcepack=12 / datapack=6945 / plugin=5 |
| `sxcl_mods_curseforge_search_url()` | `/v1/mods/search?gameId=432&index=…&pageSize=…&classId=…&gameVersion=…&modLoaderType=…`（**key 绝不进 URL**，走请求头；pageSize 夹到 CF 上限 50）|
| `sxcl_mods_curseforge_search_parse()` | `data[]` → 复用同一个 `sxcl_mod_hit`（id 数字转字符串、logo.url 当图标、authors[0].name 当作者、latestFiles[0].gameVersions 当支持版本、totalCount 当总数）|

**还没做（明说）**：带 key 的**联网查询**没接（这一轮只到 URL + 解析 + no-key 状态）；

CF 结构已就绪"，不是"双源都已通"。

### 14.1 CF 的挑文件 + 带 key 的联网查询（补上，2026-09-22 晚）

* `sxcl_mods_curseforge_versions_url(mod_id, mc, loader)` → `/v1/mods/<数字 id>/files?gameVersion=…&modLoaderType=…&pageSize=50`；
* `sxcl_mods_curseforge_versions_parse()` → `data[]` 映射到**同一个** `sxcl_mod_file`：
  `fileName/displayName/downloadUrl/fileLength`；`hashes[]` 里 **`algo==1` 才是 SHA-1**（不是第一个！）；
  `dependencies[]` 里 **`relationType==3`** 才算必装；`gameVersions[]` 里游戏版本与加载器名混在一起，统一塞进去给
  `sxcl_mods_pick_file` 用（于是 CF 与 Modrinth 走的**是同一套挑文件逻辑**）；
  **没有直链的文件**（作者关掉了 API 分发）直接跳过 —— 如实少一条，不造假 URL。
* CLI：`mods search|files … --repo curseforge [--key K]`，key 也可以填在设置里
  （`mods.curseforge_api_key`）。带 key 的请求走**带自定义头**的那条 HTTP。

**真机验收（用假 key，验的是"路通不通"）**：

`
$ sxcl-dl mods search jei --repo curseforge --key 00000000-0000-0000-0000-000000000000
请求(带 x-api-key 头,key 不进 URL): https://api.curseforge.com/v1/mods/search?gameId=432&index=0&pageSize=20&searchFilter=jei&classId=6&gameVersion=&modLoaderType=0
WARN net | GET https://api.curseforge.com/v1/mods/search?... -> 状态=403 字节=0 耗时=3844ms 被服务器拒绝（HTTP 403）
取 CurseForge 失败: 被服务器拒绝（可能是地区限制或反爬）（HTTP 403）：…
`

403 = **服务端确实收到了请求并用 key 拒了它** —— URL、请求头、TLS、错误回传整条链路都通了，
差的只是一把真 key（用户自己申请）。顺带修了一个真坑：手工建 Qt 传输之后**必须先调
`sxcl_transport_qt_bootstrap()`**，否则 HTTPS 会报 `No functional TLS backend was found`
（引擎那条路内部会做，手工建的要自己来）。

`tests/mods_test.c` 增到 **124 项**（CF 文件那一半 16 项：sha1 认 algo==1、必装依赖认 relationType==3、
没直链的跳过、挑文件与 Modrinth 同口径）。

### 14.2 界面接线：来源滑块 + key 那一栏（2026-09-22 晚）

| `SXCL_UI_MODS_INSTALL=N`（+`_DELAY`） | 点第 N 个「装」（取版本 → 挑文件 → 工作线程下载校验 → 落盘） |

**真机验收（都跑过）**：

  OCR 到这句原文）。

**当天踩的坑**：模组页在下载页的 stack 里**有两份**（MOD 一份、光影一份），两份的搜索框同名。

### 15 P0：匹配字段被截断 → 支持一长串游戏版本的包"永远装不上"（2026-09-22 晚，真机复现）

**症状**：`sxcl-dl mods files HVnmMxH1 --mc 1.20.1 --loader iris` 列出 24 个版本、每一条都写着
`iris optifine`，末尾却是「**没有适合这个实例的版本**」。

**根因**：`sxcl_mod_file.game_versions` 当初是按"显示字段"做的 —— 只装**前 6 个**（`loaders` 前 4 个），
而 `sxcl_mods_pick_file` 是拿它**匹配**的。Complementary Reimagined r5.9.3 的 `game_versions` 有
**76** 项，前 6 项是 `1.7.10…1.8.4`，`1.20.1` 排在第 8 位之后 → 加载器对得上、版本对不上 →
判"没有能用的文件"。

**影响面**：**任何支持版本数超过 6 的模组/光影**（真机搜出来的第一条就中招）。
这不是 CF 独有：Modrinth 那条路一样中招，等于最常见的那批包**全都装不上**。

**修法**：

* 匹配字段不截断：`game_versions[1024]` / `loaders[256]`，装到缓冲满为止；
  要截断显示是**界面**的事（mods.h 里写清了为什么）；
* CF 的 `gameVersions[]` 里版本号与加载器名混在一起 → 按"开头是不是数字"分成两堆
  （`split_cf_game_versions`）。不分堆的话，支持十几个版本的模组会把 `Forge` 挤出缓冲 ——
  同样是"把能装的判成不能装"。

**回归**：`tests/mods_test.c` 新增 `test_many_versions`（12 个版本的夹具，目标版本排第 8）
+ CF 第三条夹具（12 个版本 + `Forge` 排最后）；总数 **124 → 138 项**。

**真机复验**：同一条命令现在输出 `挑中(装这个): ComplementaryReimagined_r5.9.3.zip`。

### 16. B7（Quilt）现状：代码就位，真机 e2e 卡在源站速度上（2026-09-22 晚）

**代码侧已做完的**：

* `sxcl_loader_kind_implemented()` 已放开 Quilt（docs/22 §10）；
* 库的 maven 根换成 `MAVEN_QUILT`（`installer.c` 顶部）—— Quilt 的库**不在** Fabric 的
  maven 上，用 Fabric 那个会 404；
* 候选清单来自 `meta.quiltmc.org/v3/versions/loader/<mc>`（快、小）。

**缺的那一块：安装器 jar**（`org.quiltmc:quilt-installer:0.15.1`，**8,734,533** 字节）。
它**只有一家在托管**，本轮实测：

| 候选 | 结果 |
|---|---|
| `maven.quiltmc.org/repository/release/...` | 200；30 秒只给 0.94MB（**32.7KB/s**），且有「连上一个字节不来」的时段 |
| `bmclapi2.bangbang93.com/maven/org/quiltmc/...` | **404** |
| `repo1.maven.org/maven2/org/quiltmc/...` | **404** |

**这一轮为它顺手修的两条引擎毛病**（详见 `docs/15-下载源与镜像优先.md` §7）：

1. **不再为一个「没履历」的备选，把正在出数据的慢源赶走** —— `better_live_source`：
   只有备选没被判死、且失败次数不超过当前这一路时才「换路」；候选多轮走
   （`SXCL_SOURCE_ROUNDS`），一轮有进展就再来一轮。改之前：8.7MB 的文件下到 **1.19MB**
   就被换路，备选 404，整条失败。
2. **Qt 传输加「停滞看门狗」** —— 60 秒一个字节都不来就放弃本次尝试（保留已下部分，续传/换路），
   而不是无限期挂着。改之前实测：进程 CPU 0.09s、九分钟零进展、界面还在「正在下载」。

**真机证据**：同一条 `sxcl-dl get <官方 URL> ... --mirror <404 那条> --verbose`，
改之前停在 1.19MB 后死等；改之后**一直在往前爬**（0.00~0.39MB/s 之间跳，没有再永久停摆），
写这份文档时到 **57%**。

**还没做（明说）**：

* Quilt 的「安装 + 启动」e2e 依旧**没有真机证据** —— 卡在源站速度上，不卡在我们的代码上；
* `launcherMeta`（HMCL 式）那条路**没做**：Quilt 的 meta 里本来就有 `launcherMeta.libraries`
  与 `mainClass`，照着它直接拼版本 JSON 就**不需要那 8.7MB 的安装器** —— 这才是绕开这家慢源的
  正解，属于下一步（要么等官方源恢复到可用速度，要么做这条路）；
* GUI 里还不能装 Quilt（下载配置页的加载器选项没接 Quilt 这一档）。

**18:32 补测（分片）**：给 CLI 加了 `--conn N`（单文件分片，门槛 文件 ≥4MB 且每片 ≥1MB），
`--conn 8` 前 45 秒拿到 2.5MB（≈55KB/s，比单连接快一个量级），随后整条 IP 被掐到 ≈2KB/s，
停在 **40.9%（3.40MB）**。**这家源对本机网络不可用** —— 分片也救不回来。
结论不变：Quilt 的安装 e2e 缺真机证据，缺的是「拿得到那 8.7MB」，不是代码。

### 17. OptiFine 的「静默安装」是个假象（2026-09-22 晚，真机）

**先说好消息**：BMCLAPI 其实**有** OptiFine 镜像，而且很快 ——

```
$ curl -I https://bmclapi2.bangbang93.com/optifine/1.20.1/HD_U/I6
HTTP/1.1 302 Found
Location: /maven/com/optifine/1.20.1/OptiFine_1.20.1_HD_U_I6.jar
# 跟着下载：7,145,205 字节，几秒钟下完（对比 Quilt 那家 32KB/s）
```

所以 `install_worker.cpp` 里那句「OptiFine 没有稳定的 maven 直链」**不准确** —— 官方站确实没有，
但镜像有，而且 URL 可以由「MC 版本 + HD_U + I6」三段拼出来（`/optifine/<mc>/<type>/<patch>`）。

**坏消息（这才是真坑）**：把 jar 拿到手、走我们已经有的沙箱安装（`installer.c:580` 的
`--installClient` 那条命令）之后 ——

```
$ sxcl-dl loader optifine HD_U_I6 1.20.1 <临时目录> --installer <本地 jar> --java D:/jdk17/bin/java.exe
  [ 20%] OptiFine 正在安装（静默，不打图形界面）
      [out] OptiFine Version: OptiFine_1.20.1_HD_U_I6
      [out] Minecraft Version: 1.20.1
      [out] OptiFine Edition: HD_U_I6
      ...然后就没有然后了

$ Get-Process java | Select MainWindowTitle
OptiFine Installer          # <- 它把**图形界面弹出来了**，在等你点
```

沙箱目录里只有 `appdata/.minecraft/launcher_profiles.json` 与
`appdata/.minecraft/versions/1.20.1/{1.20.1.jar,1.20.1.json}`，**没有任何产物**：
OptiFine 的安装器是 Swing 应用，`--installClient` 只是告诉它装到哪，**不隐藏窗口**。
`installer.c:2252` 那句「静默，不打图形界面」与实测不符（代码注释也是文档，得改）。

**结论**：

* OptiFine 的「点一下就好」在现在的实现里**做不到**，而且不是网络问题；
* 要做只有 HMCL 那条路：**解包安装** —— 从安装器 jar 里取 OptiFine 自己的库/类，自己拼版本 JSON，
  全程不跑安装器 GUI（`installer.c` 里已经有「方式 B:解包安装」的骨架，但 OptiFine 的产物布局要单独摸）；
* **本轮没做**，只把现象钉死；在没做之前，UI 上把 OptiFine 摆成可选并让用户点下去，就是**假装**。
