# 安卓：图形栈与版本兼容（实测笔记）

记录实测结论，供后续 Android 阶段决策用。**只写实测过的，不写推测。**

## 测试设备与图形栈

| 项 | 值 |
| --- | --- |
| GPU | **Mali-G615 MC2** |
| OpenGL ES | **3.2**（设备原生） |
| 图形包装层 | **Krypton Wrapper Release 0.4.5**，对外暴露 **OpenGL 3.1** |

结论：Mali 这类"ES 3.2 + 包装层"的组合已经能提供启动现代版本所需的 GL 3.1 能力，
**不需要我们自己写图形驱动**（原先设想的驱动工作的必要性因此显著下降）。
启动层要做的是：正确识别设备可用 GL 版本、按版本选择渲染路径（原版 / 兼容层），
而不是接管图形栈。

## Minecraft Java 版版本兼容（HMCL 实测）

| 版本 | 结果 | 备注 |
| --- | --- | --- |
| Java 版 **26.2** | **可以进入游戏** | 与上面的图形栈组合可用 |
| Java 版 **26.3** | **无法启动** | 26.3 于 **9/15** 发布，**9/16** 测试；初步怀疑"版本过新"（伴随的库/清单变动尚未被第三方启动器跟进） |

## 由此得到的启动器设计要求

1. **版本降级建议**：当"最新版本"启动失败、且失败原因落在"库/清单解析或极新版本"这一类时，
   界面应直接给出"换上一个版本试试"的建议，而不是只丢一堆日志。判据要来自日志解析，不是猜测。
2. **区分故障类型**：把启动失败分成三类并分别提示——
   - 图形栈（GL 版本/渲染器不匹配、包装层版本过旧）
   - 版本支持（新版本的库/清单尚未适配）
   - 账户与网络（登录、资源下载不完整）
3. **极新版本的保守策略**：对发布不足若干天的新版本，默认在"可选"里提示风险，
   与国内启动器通行做法一致（避免用户撞上当天发布的新版本而误以为是启动器坏了）。
4. **日志解析是硬需求**：上面两条都依赖"读得懂日志"。启动层必须把游戏输出、
   `hs_err_pid*.log`、`crash-reports/*` 都接住并归类（Python 版已有雏形，C 版照搬语义）。

## 渲染后端策略（要不要自研 Vulkan 适配？）

实测：26.2 在安卓上把图形 API 切到"Vulkan（实验性）"会**回退到 OpenGL**。
这说明当前设备/包装层组合下，Java 版的 Vulkan 路径不满足它的启用条件——但要先分清
"缺的是哪一层能力"，再决定投不投资源。分三层看：

| 层 | 内容 | 谁来做 | 我们的判断 |
| --- | --- | --- | --- |
| **驱动层** | 把 GL 调用翻译成 Vulkan 命令（Zink / Krypton / ANGLE 那一类） | Mesa / Google / 社区 | **不做**。这是几万到十几万行、需要长期跟进的工程；设备已有 Krypton 提供 GL 3.1，自研投入产出比极低 |
| **渲染器层** | 直接替掉游戏渲染器（Java 版的 Vulkan 渲染由 **Mod** 实现，如 VulkanMod） | Mod 作者 | **不做**，但**要集成**：启动器提供"一键启用 Vulkan 渲染（实验）"，装 Mod 而不是写驱动 |
| **启动器层** | 能力探测 + 后端选择 + 翻译层管理 + 参数注入 + 失败回退 + 日志归类 | **我们** | **做**。这才是"四系统不可用时顶上"的正确形态 |

### 启动器层要做的具体事（四平台通用）

1. **能力探测**：读 `GL_VERSION`/`GL_RENDERER`/Vulkan 版本与扩展（Android 侧可从 `/system/vendor/etc/vulkan/icd.d`、
   设备属性、或包装层自报拿线索）。产出一份"这台机器能用什么后端"的判定表。
2. **后端选择与参数注入**：GL(原版) / GL(包装层: Krypton、ANGLE、Zink) / Vulkan(经 Mod) 三条路，
   各自对应不同的环境变量与 JVM 参数；选择结果写成可复现的启动配置。
3. **失败回退**：Vulkan 起不来 → 自动退回 GL(包装层) → 再不行退回软渲染，并把每一步的原因写进任务日志。
4. **一键启用 Vulkan 渲染**：在模组加载器基础上装 VulkanMod 这类 Mod（版本匹配、依赖齐全、可一键卸载），
   而不是自己接管图形栈。
5. **拒绝猜测**：任何"某设备不可用"的结论都必须来自实测日志，不许写死在代码里。

### 为什么这条路线能"顶上"

- Windows / Linux：ANGLE（GL→D3D11）与 Mesa/Zink（GL→Vulkan）都已成熟，作为 GL 不可用时的替补。
- macOS：Apple 早已停更 OpenGL，Mesa/Zink + MoltenVK 是常见解法。
- Android：ANGLE / Krypton / Zink 三选一，按设备实测结果挑。
- 四平台共用同一套"探测 → 选择 → 注入 → 回退"逻辑，差异只在具体后端库与参数。
