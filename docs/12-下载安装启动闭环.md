## 2. 线程模型(硬要求:主线程绝不阻塞)

   界面线程(Qt 主线程)                     工作线程(每个 worker 一条,跑完即退)
   ────────────────────                     ──────────────────────────────────────
   InstallWorker::start()  ──QThread::start()──►  run():
   立刻返回                                        读下载设置(sxcl_settings_resolve_download)
                                                   建 sxcl_engine_opts
                                                   拼 sxcl_install_plan
                                                   emit planReady(ids, names)      ─┐
                                                   sxcl_install_run(&req,&res)      │ Qt 自动连接
                                                     │                              │ = 队列投递
                                                     └─ 进度回调(来自**引擎的工作线程**)┤ 到界面线程
                                                          emit logLine / progress  ──┘
                                                   emit finished(ok, cancelled, …)
   cancel() ── m_cancel.store(true) ──────────►  is_cancelled 回调看到非 0 -> 核心库收尾

要点(每条都有依据,不是"应该没问题"):

1. **进度回调可能来自任意引擎线程**。`include/sxcl/install.h:194-197` 原文:
   "阶段开始/结束/清理/结束事件在调用 sxcl_install_run 的那个线程里发;但**下载阶段的进度事件
   来自引擎的工作线程** … 同一个回调可能被不同线程调用"。所以 worker 里**不直接碰控件**,
   只 `emit` 信号,由 Qt 按接收者线程(界面线程)排队投递。
2. **取消是一个原子位,不是排队调用**。`cancel()` 只做 `m_cancel.store(true)`:
   它必须能在界面线程**同步**生效 —— 如果做成 `QMetaObject::invokeMethod(Queued)`,
   而工作线程正阻塞在 `sxcl_install_run` 里(事件循环没转),那条消息根本送不进去。
3. **节流在 worker 里**:最多 10 次/秒(与 Python 下载进度页的 100ms 节流同口径),
   但**阶段切换 / 清理 / 结束一定发得出去**(否则界面会停在旧阶段)。
4. **析构先 join**:`~InstallWorker` / `~LaunchWorker` 里 `cancel() + quit() + wait()`。
   不 detach —— 否则线程会拿着已析构的 `this` 回调,那是崩溃不是"偶发"。
5. **线程归属**:worker 对象自己是页面(界面线程)的子对象,`moveToThread(m_thread)` 后
   槽函数在 `m_thread` 里跑;`QThread` 对象又是 worker 的子对象,所以析构顺序是
   `~InstallWorker`(先 join,线程已停)→ `~QObject` 删 `QThread`(已结束,安全)。

### 速度与剩余怎么来的(核心库没给)

`sxcl_install_progress` 只有 `bytes_done` / `bytes_total`(`install.h:176-191`),**没有 speed**。
worker 自己从"字节增量 / 墙钟增量"算:

    dt >= 250ms 时: speed = (bytes_done - last_bytes) * 1000 / dt
    字节回退(换阶段)时重新起算
    eta = (bytes_total - bytes_done) / speed      /* speed <= 1 B/s 或总量未知 -> -1 */

需要一把 `std::mutex` 保护(回调来自多个线程)。算不出来就报 `-1`,界面显示"—",**不编数**。

## 3. 核心 API 调用链

### 安装

    download_progress_page.cpp
      └ InstallWorker::run()                                   src/ui/workers/install_worker.cpp
           ├ sxcl_settings_default_path / sxcl_settings_open / sxcl_settings_resolve_download
           │     下载参数(workers / rate / max_conn / cache_dir)—— 与 CLI、设置页下载 JRE 同口径
           ├ sxcl_fs_mkdirs(cache_dir) + "<cache>/hashes.txt"   哈希缓存(与 sxcl-dl main.c:447 同路径)
           ├ sxcl_loader_kind_from_id(loaderType)               "none"/"forge"/"neoforge"/"fabric"/"optifine"
           ├ sxcl_install_plan_stage_count / _stage_at / sxcl_install_stage_name|_id
           │     **阶段表只认核心库这一份**(install.h:20-21 明说 UI 直接照它画行)
           ├ sxcl_install_default_io()                          真实现(取文本/下载/加载器/natives)
           └ sxcl_install_run(&req, &res)
                 req.on_progress   = cbProgress   -> 队列投递到界面线程
                 req.is_cancelled  = cbCancelled  -> 读 m_cancel
                 io.userdata       = &engine_opts  (install.c:1335-1340 取文本要用传输后端)
                 plan.engine_opts  = &engine_opts  (install.c:609      下载钩子要用)

**传输后端**:`engine_opts.transport_factory = []{ return sxcl_transport_qt_create(); }`
(`src/net/transport_qt.cpp`;`src/ui/CMakeLists.txt:61-64` 只有 `TARGET sxcl_net_qt` 存在时才链它,
并定义 `SXCL_UI_HAVE_QT_TRANSPORT=1`)。没有它时 worker **如实报**
"本次构建没有链接 Qt Network 传输后端",绝不假装在下载。

**校验一个都没放宽**:SHA-1 强校验、断点续传、已存在且校验通过就跳过(`files_skipped`)、
natives 解压、加载器安装,全部在核心库里,worker 一行都没重写、也没跳过任何阶段。

### 启动

    launch_page.cpp
      └ LaunchWorker::run()                                    src/ui/workers/launch_worker.cpp
           ├ 第一遍 sxcl_launch_run(dry_run = 1)
           │     真实走完:读版本 JSON -> 选 Java -> 写 options.txt -> 建 natives 目录 + 解 native
           │              -> 拼 argv
           │     on_line 回调里收到**核心库自己打的、已打码的**命令行
           │        (driver.c:355-378:"argv: <java>" + "  arg[i] …",accessToken 换成 ***)
           ├ 第二遍 sxcl_launch_run(dry_run = 0)   ← 只有 dryRun == 0 时才跑
           │     on_line 每行 -> sxcl_log_scan_line -> sxcl_log_kind_name -> 队列投递到界面线程
           └ 结果:sxcl_launch_result 的 exit_code / timed_out / killed_by_client /
                   conclusion_text / log.lines / natives_count …

**为什么跑两遍**:`sxcl_launch_result`(`launch.h:484-506`)**不回传 argv**,而启动页必须显示
"最终命令行"。核心库留的口子就是 `dry_run + on_line`。所以第一遍拿到命令行与 Java 探测结果,
第二遍真起进程。准备部分幂等(options.txt 重写、natives 已存在即跳过),不会重复下载。

**为什么不在 UI 里自己拼一份 argv**:拼参数要考虑 rules、classpath 分隔符、memory/GC、
natives 路径、`--offline`/`--accessToken` 语义……自己抄一份迟早与核心库漂移,
那正是"看起来能启动、实际参数不对"这类缺陷的来源。

### 身份(与 CLI 同一条核心通路)

| 场景 | 走哪条 | 依据 |
|---|---|---|
| 没有可用账户 | `LaunchWorker` + `sxcl_launch_request.offline_name` | 核心库拼出 `--offline <名字>`;名字取 `SXCL_UI_OFFLINE_NAME`,默认 `"Player"` |
| 有可用账户 | `startAccountLaunch(...)`(`dialogs/account.*` 的现成入口,**一行没改**) | `AccountSnapshot` **故意不带 access_token**(`account.h:38-55`),令牌只在账户模块内部从加密存储读出后直接交给核心库 |

所以"正版身份"不是"启动页要不要传令牌",而是"启动页根本拿不到令牌" —— 这也是
"别改账户代码、只调现成入口"的由来。账户路径下启动页先跑一遍 `dry_run` 的 worker,
所以 Java 探测结果、最终命令行(离线形态)、natives/目录检查照样能看到,页面会写明这一点。

## 4. 任务页联动

任务页 `TasksPage` 的登记 API 是 `Q_INVOKABLE`(`tasks_page.cpp:340-395`):

    addOrUpdateTask(id, title, progress, status, detail)   // 新建或更新
    updateTask(id, progress, status, detail)
    setTaskRunning(id) / setTaskDone(id) / setTaskFailed(id)
    taskCount()

主窗口在切进临时页时已经登记过一次(`main_window.cpp:445` / `:457`):

    下载页 key = "download_progress_" + 版本名     标题 "下载 <版本名>"
    启动页 key = "launch_" + 版本名                标题 "启动 <版本名>"

进度页/启动页**不需要改 main_window.cpp**:它们用 `window()->findChild<QObject*>("TasksPage")`
找到任务页,再 `QMetaObject::invokeMethod(..., Qt::DirectConnection, ...)` 按同一个 key 更新。
(TasksPage 的 objectName 就是 `"TasksPage"`,`tasks_page.cpp:310`。)

`SXCL_UI_TRACE=1` 时每次调用都会打出**真实回读**的证据行:

    [sxcl-ui] task | download_progress_1.0 -> 42% | 下载依赖库 | 下载依赖库 | 任务页卡片数=1

"任务页卡片数"是用 `taskCount()` 从任务页**读回来**的 —— "调了但没人接"不会冒充成联动成功。

## 5. 进度 / 取消语义

### 三种终态**分开**(这是硬要求)

| 终态 | 判据(核心库原文) | 页面文案 | 任务页 |
|---|---|---|---|
| 成功 | `sxcl_install_run` 返回 `SXCL_INSTALL_OK` | 阶段全绿、"安装完成"、✓ 完成 | `setTaskDone` |
| **已取消** | `result.cancelled != 0` 或返回 `SXCL_INSTALL_ERR_CANCELLED(-9)` | ⊘ 已取消(warning 色)+ "未完成的下载产物(.part)已清理" | `setTaskFailed` + 卡片写"已取消" |
| 失败 | 其它负数返回码 | ✗ 失败 + **核心库的人话原因**(原文) + 失败阶段 | `setTaskFailed` |

失败时显示的是 `sxcl_install_result.error` **原文**(例如"下载客户端 jar 失败: …"),
不是"失败"两个字;`message` 还会拼上 `sxcl_install_stage_name(result.fail_stage)` 的中文阶段名。
`result.retryable` 会追加"可以重试 / 不建议直接重试"。

### 取消的完整语义(install.h:34-37 原文)

    ① 正在跑的阶段被叫停(引擎走 sxcl_engine_cancel,安装器走 request 里的 is_cancelled)
    ② 未完成产物被清理(所有计划内任务的 <dest>.part / <dest>.part.json,以及本次下的安装器 jar)
    ③ 返回 SXCL_INSTALL_ERR_CANCELLED(与普通失败可区分)

界面侧只做两件事:把 `cancel()` 的原子位置 1;把按钮改成"正在取消…"。

### 启动的取消(如实说明边界)

`sxcl_launch_run` **没有**"给我进程句柄"的入口(`process.h` 只有 `on_line` 回调),
所以取消走 `launch.h:477-479` 明写的那条路:**`on_line` 返回非 0 = 请求终止进程**。
边界要说清:**游戏一行输出都没有时,取消要等到下一次输出才生效**;准备阶段(还没起进程)
的取消则立刻生效。`killed_by_client` 与 `m_cancel` 任一为真都算"已取消",不算成功。

### 阶段名(中文)来自哪里

`sxcl_install_stage_name()`(`install.c` 的表)—— 界面**不另写一份阶段名表**。
进度页的顶部大字 = 核心库给的中文阶段名 + `(本计划第几个/共几个)`;
阶段行在 `planReady` 到达后按 `sxcl_install_plan_stage_*` **重画**(构造期先摆 Python 那份行表,
只用于"计划还没回来"的一瞬间)。

## 6. 统一错误出口 + 自动复制剪贴板

用户要求:"所有报错自动复制到剪贴板"。实现是**一处**,不是每页各写一遍:

    src/ui/workers/ui_error.{h,cpp}
      UiErrorContext { page, action, reason, detail, title, warning }
      reportUiError(ctx)  -> 组完整报告 + 去重 + 复制 + stderr 追踪,返回报告全文
      pushUiError(host, ctx, ms) -> 上面那些 + 一个 InfoBar(content 末尾带"完整错误已复制到剪贴板")

报告内容(与用户点名的四项一一对应):

    === Silent X Craft Launcher 错误报告 ===
    时间: 2026-09-21 15:12:03
    页面: 下载进度页 / download_progress_1.0
    操作: 安装 Minecraft 1.0(实例 1.0,加载器 none)
    原因: <核心库人话 + 原始错误码/HTTP 状态码/URL —— 调用方原样传入,本层不改写>
    详情: 错误码 -4(client_jar)· 阶段 2/10 …
    启动器: Silent X Craft Launcher 0.1.0
    Qt: 6.x   平台: windows / x86_64
    可执行: …\sxcl-ui.exe

三条硬约束:

* **同一个错误只复制一次** —— 去重键 = `页面|操作|原因`;重复出现只在界面显示,不再覆盖剪贴板
  (用户还在粘贴上一个错误时被刷新刷掉是最烦的)。
* **剪贴板不可用就静默降级** —— `QGuiApplication::clipboard()` 为空、平台后端不支持、
  或"接受了 setText 但没真的落地"(用**读回来比对**判定),一律只写 stderr 追踪,不弹错。
* 桌面与 Android **同一份代码**:走 Qt 的剪贴板抽象,本层没有任何平台分支。

已接线的调用点:`download_progress_page`(安装失败 / 版本已存在)、`launch_page`
(启动失败 / 账户入口失败)、`download_config_page`(重名 / 无法开始下载)、`home_page`(启动器未初始化)。
其他页面(settings / versions / dialogs)接同一入口只需一行 —— 那些文件不在本次改动范围,
已在交付报告里点名。

## 7. 复现命令

全部**离屏**运行,绝不开可见窗口;超时兜底杀进程。

> 注意 `SXCL_UI_VERSION` 是**显式钉死的版本 id**,走的是 main_window.cpp:320-334 既有的验收通路,
> **不代表版本列表可用**。产品路径是"版本页/配置页选版本 → 配置页 → 进度页",版本 id 由用户选。

    $env:SXCL_UI_GAME_DIR       = 'D:\sxcl-ui-e2e\game'

### 7.3 界面启动(离线真起进程)

同上,但**不设** `SXCL_UI_LAUNCH_DRY_RUN`;可选 `SXCL_UI_OFFLINE_NAME=<名字>`。

## 8. 已知限制(明说,不藏)

1. **加载器版本列表还没接**。下载配置页的四行加载器(Forge/NeoForge/Fabric/OptiFine)
   停在"加载中…" —— 它们的候选版本要**联网取目录**(`loader_catalog.h` 的 maven-metadata / OptiFine 网页),
   这段取数不在本次改动范围。所以今天从界面走得通的是**原版**路径;
   一旦列表接上,`loaderType` / `loaderVersion` 是原样传给 worker 的,不需要再改接线。
2. **安装器地址由界面层拼**。`install.h:118-119` 明说 `installer_url`"由加载器版本列表层给,
   本层不会自己拼 URL"。界面层就是那个"列表层",`install_worker.cpp` 里按各家 maven 布局拼
   Forge / NeoForge / Fabric 三条直链;**OptiFine 没有稳定直链,如实返回空**,
   worker 报"OptiFine 的安装器地址拿不到……"(不猜一个 URL 然后拿 404 冒充网络故障)。
3. **启动拿不到 PID**。`sxcl_launch_result` / `sxcl_process_result` 都没有 pid 字段
   (`process.h:32-35` 只有 exit_code / timed_out / killed_by_client)。
   要显示 PID / 单独结束游戏进程,需要**改核心库**(`include/sxcl/process.h` 加 pid)——
   按纪律没有擅自改,已报到主线。
4. **启动取消要等下一次输出**(见 §5)。
5. **账户路径不显示命令行**。账户令牌不经界面(`AccountSnapshot` 不带 token),
   正版启动由 `startAccountLaunch` 独立入口执行,启动页只能显示"准备阶段"的离线形态命令行,
   页面里已明确标注。
6. **两个 worker 各跑两遍准备**(`dry_run` 一遍 + 真跑一遍)。准备是幂等的
   (options.txt 重写、natives 已存在即跳过),换来的是"最终命令行"能显示出来。
7. **Android 的 PC 版 Java 运行时**:Mojang 官方 runtime 没有 android/arm64 版本,
   真机要跑 Java 版 MC 需要另找可再分发的 OpenJDK arm64 构建 + 图形翻译层(另开专题,见交付报告)。

### 9.6 本次改出来的三个真缺陷(都是"跑真数据"才暴露的)

1. **`io.userdata` 没填** -> 阶段 0 直接失败:
   "取版本清单失败: 取文本需要传输后端(engine_opts.transport_factory 为空)"。
   `sxcl_install_default_io()` 返回的是**静态常量表**,`userdata == NULL`;
   而取清单正是从 `userdata` 里拿 `engine_opts` 的(`install.c:1335-1340`)。
   修法:复制一份 IO 表再填 `userdata = &opts`。
2. **dry-run 那一遍的 argv 被当成"游戏输出"** -> 真启动时,界面先把整条命令行灌进日志框。
   根因:回调里判的是界面的 `m_request.dryRun`(真启动时也是 0),而不是**当前这一遍**。
   修法:加 `m_collectingCommand` 标志,只在第一遍收命令行。
3. **验收钩子写了假证据** -> `SXCL_UI_TASKS_AFTER_MS` 原先用
   `invokeMethod(window(), "switchToRoute")`,而 `switchToRoute` **不是** `Q_INVOKABLE`:
   调用静默失败、追踪行却照样写"已切到任务页"。
   修法:改成**点侧栏「任务」按钮**(真正的用户路径),并且**回读 `currentRouteKey()`** 再打印结果。

### 9.7 构建注意(踩过,留给后来人)

MSVC 有一次**没有**因为源文件改动重建 `ui_paths.obj`(对象文件时间戳比源文件新),
表现为链接期 `LNK2019` 未解析符号。`touch` 源文件后重建即通过。
改完 `src/ui/workers/*` 之后如果链接报"某个新函数未解析",先确认对象文件真的重建了。
