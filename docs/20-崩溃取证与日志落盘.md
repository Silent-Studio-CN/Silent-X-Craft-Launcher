# 20 崩溃取证与日志落盘

> 用户原话:"不读 crash-reports、不读 latest.log、游戏输出也不落盘"不行 —— 这个必须做。
> 本文记录这件事的现状、做法、验收与**还剩什么没做**。

## 1 问题(改动前的真实状态)

| 环节 | 改动前 | 后果 |
| --- | --- | --- |
| 游戏输出 | 只走 `driver.c` 的 on_line 回调 → 界面 uiTrace(默认不落盘) | 用户报障时我们手上**什么都没有** |
| crash-reports | 只出现在**文案**里("可以看 crash-reports/") | 一个字都没读过;真死因在磁盘上躺着 |
| latest.log | 完全没读 | 编码还可能是 GBK/UTF-16,读了也可能乱码 |
| 结论 | 8 类 + 每类一句人话 | "图形栈出问题"用户没法照着做 |

## 2 做法

### 2.1 游戏输出落盘(`include/sxcl/log.h` 第 5 节 + `src/core/log.c`)

* 每一行 stdout/stderr 由 `driver.c` 的 `driver_on_line` 调 `sxcl_log_game_line()`;
* **攒批**:32 行一批、距上次落盘 ≥300ms、或显式 flush(进程退出/导出前/关通道/shutdown)才写盘,
  一批只 `fwrite` 一次 + `fflush` 一次 —— 每行都 flush 会把磁盘刷爆(游戏一秒几百行);
* 时间戳在**收下的那一刻**定好(攒批不会让整批共用一个时间);
* 行格式与别的模块一致:`YYYY-MM-DD HH:MM:SS.mmm INFO  game | <原始行>`,所以
  `grep " game | "` 就是全部游戏输出;
* 落盘前先过 `sxcl_log_mask_secrets`(凭据不进磁盘第二份),模块名固定 `game`,默认开;
  设置文件 `log.game=0` 或环境变量 `SXCL_LOG_GAME=0` 关掉,级别调到 WARN 也会停收;
* 单行超过 1024 字节截断并计数;统计在 `sxcl_log_stats` 的 `game_lines/game_flushes/game_dropped/game_truncated`。

### 2.2 崩溃取证(`include/sxcl/crash.h` + `src/core/diag/crash.c`)

进程退出后,**崩了**(退出码非 0 / 归到崩溃类)才去读游戏自己写的那两份文件:

1. `<game>/crash-reports/*.txt`:只取**最近的、非空的**一份(0 字节/纯空白的历史报告跳过,
   "最近"按修改时间);`---- Minecraft Crash Report ----` / `Description:` / `Caused by:` 由
   `sxcl_crash_report_marker` / `sxcl_crash_report_description` 认出来;
2. `<game>/logs/latest.log`:缺失/为空时退到 `debug.log`,再不行退到老版本(1.7 之前)的
   `logs/client-*.log` —— FCL/老版本玩家的日志是这个名字;
3. **编码先探后转**(见 2.3),大文件只读**尾部**(崩因在最后),但行数按整个文件数;
4. 读到的每一行都喂进 `sxcl_log_summary_add` —— 与 stdout **同一套规则、同一张原因表**,
   所以"从哪读到的"不会让结论分叉。界面点"查看详情"走同一个入口
   (`sxcl_launch_scan_artifacts`),CLI 是 `sxcl-dl crash <游戏目录>`。

### 2.3 编码探测(`include/sxcl/text.h` + `src/core/diag/text.c`)

实测:中文 Windows 上的 MC 日志是 **GBK/CP936**(直接按 UTF-8 读就是"锟斤拷"),也有 UTF-16。

* 探测键:`empty/ascii/utf-8/utf-8-bom/utf-16le/utf-16be/gbk/ansi/binary`;
* UTF-16 有 BOM 按 BOM;无 BOM 用"零字节是否稳定落在一侧"的启发式(ASCII 为主的日志有效);
* GBK 转换:Windows 走系统 ANSI 代码页(`MultiByteToWideChar`),POSIX 走 `iconv`;
  安卓 bionic 的 iconv 不保证存在,退回 Latin-1 直通(**至少输出仍是合法 UTF-8**);
* 大文件只读尾部时,**编码按文件头探**(尾部没有 BOM,拿尾部去猜会猜错);
* 坏字节换成 U+FFFD、控制字符换成 `.`(日志里看得见而不是一团乱码)。

### 2.4 结论表做厚(`include/sxcl/launch.h` 第 3b 节 + `reason_lang.inc` + `logscan.c`)

* **63 个原因键**(对标 PCL 的 48 项 / HMCL 的约 60 条正则),例如
  `out_of_memory` / `out_of_native_memory` / `jvm_32bit` / `heap_too_large` / `jvm_fatal` /
  `graphics_driver_intel|nvidia|amd|mesa|adreno|mali|powervr|software` / `graphics_driver_outdated` /
  `opengl_too_low` / `glfw_init_failed` / `mod_duplicate` / `mod_resolution_conflict` /
  `mod_missing_dependency` / `mixin_failure` / `missing_java_library` / `corrupt_jar` /
  `android_noexec` / `android_selinux_exec` / `crash_unknown` …
* 每个键有**中英两份**短名 + **可执行建议**(不抄 PCL/HMCL 的文案),表在
  `src/services/launch/reason_lang.inc`(与 `lang_table.inc` 同一套写法与覆盖规则:
  用户语言包可以用 `crash.reason.<键>` / `crash.reason.<键>.advice` 逐条覆盖);
* 判定规则是`logscan.c` 的 `kReasonRules` 表:每条 = 原因键 + 分数(越大越具体)+
  任一命中 + 全部命中(可空)。**子串而非正则**:仓库没有正则引擎,而这些句型都是固定的;
* **门槛**:纯 INFO 的环境行("OpenGL Renderer: Intel(R) UHD Graphics 630")不进规则表 ——
  否则每次正常启动都会报一个不存在的"核显驱动问题";WARN/ERROR 行直接进,INFO 行必须自带问题词;
* 汇总取分数最高的一条,分数与"类别"(conclusion)互补:类别回答"属于哪一类",
  原因键回答"用户该改什么"。

### 2.5 一键导出(`include/sxcl/logexport.h` + `src/core/diag/export.c`)

* 打包:启动器 `sxcl-*.log`(默认最新 3 份)+ `<game>/logs/latest.log`(可选 debug.log)
  + `<game>/crash-reports/*.txt`(默认最新 3 份)+ 一份 `EXPORT-INFO.txt` 说明;
* **写盘前打码**:token / UUID / 玩家名 / 路径里的用户名(Windows 用户目录、/home/)
  → `***`,复用 `sxcl_log_mask_secrets`(URL 的敏感查询参数口径与 `sxcl_log_mask_url` 只有一份);
* **打包方式 = store(method 0,不压缩)**:仓库里只有 zip 的**读**侧,写侧是本模块自己写的
  store 打包器(本地头 + 中央目录 + EOCD + CRC32)。如实说明:没有压缩,换来的是
  "任何解压工具(以及我们自己的 `sxcl_zip_open`)都能打开"这个确定性;
* 入口:界面启动页的「导出日志」按钮、CLI `sxcl-dl logs export`。

### 2.6 顺带补上的两个真问题

* **命令行落盘**:实际起进程前把**打码后**的 argv 写进运行日志(`driver.c` 的 `log_argv`)——
  以前只有 dry-run 且界面自己拼时才有一份;"用户到底跑了什么"必须有唯一凭据;
  打码名单:`--accessToken --session --uuid --username --xuid --clientId`;
* **CLI 也初始化日志**:以前只有界面 `main.cpp` 调 `sxcl_log_init`,命令行一条日志都不落盘,
  "导出日志"在 CLI 上等于空包。

## 3 验收(真跑,不是"应该能行")

### 3.1 桌面真崩溃端到端

本机没有真实 MC 1.0 客户端 jar(Mojang CDN 在本机持续超时,我们自己的下载器两次
`校验失败(hash-mismatch)`/`Operation timed out`),所以用**真 Java 程序**做"像 MC 1.0 的入口类"
的夹具(`net.minecraft.client.Minecraft`),它做的四件事全是真的:

1. 真把 `-Xmx64m` 吃光(JVM 自己抛 `java.lang.OutOfMemoryError: Java heap space`);
2. 真写 `logs/latest.log`(**GBK 编码**);
3. 真写 `crash-reports/crash-<时间>-client.txt`(MC 的真形状,含 Description/Caused by);
4. 真以未捕获的 OutOfMemoryError 退出(退出码 1)。

命令与输出(节选,完整见提交说明):

```text
> sxcl-dl launch 1.0-fixture <game> --java D:\ProgramData\JAVA\Jdk26.0.2\bin\java.exe --memory 64 --offline Steve
Java: D:\ProgramData\JAVA\Jdk26.0.2\bin\java.exe (Java 26.0.2)
退出码: 1   用时 0.20 s
结论: 内存不足(Java 堆耗尽):把设置里的『最大内存』调大(如 4096MB)…
原因键: out_of_memory(内存不足(Java 堆耗尽))
崩溃报告: <game>\crash-reports\crash-2026-09-21_20.42.25-client.txt(纯 ASCII,23 行)
latest.log: <game>\logs\latest.log(GBK(中文 Windows 的 ANSI),4 行)
```

我们自己的日志(`logs/sxcl-20260921-204225.log`)里的游戏输出:

```text
2026-09-21 20:42:25.252 INFO  game | [00:00:00] [main/INFO]: Loading Minecraft 1.0-fixture …
2026-09-21 20:42:25.282 INFO  game | [00:00:03] [main/ERROR]: java.lang.OutOfMemoryError: Java heap space
2026-09-21 20:42:25.335 INFO  game | Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
2026-09-21 20:42:25.336 INFO  crash | 崩溃取证:报告=…(ascii,23 行/共 1 份) latest.log=…(gbk,4 行) 喂入 27 行
```

### 3.2 导出包

`sxcl-dl logs export <game> out\sxcl-logs.zip --log-dir <logs>` → 6 个文件 + 说明文件,
用 **PowerShell 的 Expand-Archive**(第三方 zip 读侧)能原样解开;包里的 latest.log 是
正确的 UTF-8 中文(GBK 探测生效),明文玩家名 0 次出现。

## 4 还剩什么没做(如实)

* **zip 只打包不压缩**(store)。要压缩就得再写一个 DEFLATE 编码器,或者引第三方库;
  当前选择是"标准 zip + 不压缩",代价是包大一点;
* **界面只加了「导出日志」按钮**:导出完成用 InfoBar 报路径,没有"导出后自动打开目录/复制路径";
* **原因键没有做独立的 UI 面板**:键与建议进的是日志视图与任务卡明细(detail),没有单独一栏;
* **没有真实 MC 1.0 jar 的那次验收**(网络原因),夹具覆盖了同样的四条行为,但不是官方客户端;
* crash-report 的 `Stacktrace` 段落只做逐行分类,没有做"按帧归并/给模组作者看"的结构化展示;
* 平板(FCL/安卓)那侧本任务**没有实测**:编码与编码键都支持,但安卓真机没跑过。
